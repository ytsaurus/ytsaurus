# Ресурсы

Ресурс — это компонент, который загружается до создания вычислений и используется во время
исполнения джобов: соединение с внешней базой, файл, пул клиентов. Ресурсы объявляются в секции
`resources` спецификации пайплайна (поля описаны в справочнике `TResourceSpec`), а вычисление
запрашивает нужные ему ресурсы через `required_resource_ids` своей спецификации.

Класс ресурса наследуется от `TResourceBase` (`library/cpp/resources/resource_base.h`) и
регистрируется макросом `YT_FLOW_DEFINE_RESOURCE`. Один инстанс ресурса создаётся на процесс
воркера и разделяется всеми джобами; конструктор обязан быть лёгким, тяжёлая инициализация
выполняется в `Load`.

## Контроллер ресурса

У ресурса может быть контроллерная часть — объект, работающий на контроллере пайплайна.
Типичный сценарий: контроллер обнаруживает новую версию внешних данных и рассылает её координаты,
а каждый воркер самостоятельно скачивает данные и переключается на них.

Класс ресурса связывается с контроллером типом `TController`; по умолчанию это
`TNullResourceController` — тривиальный контроллер, который ничего не публикует:

```cpp
class TMyResourceController
    : public TResourceControllerBase
{
public:
    NYTree::INodePtr BuildTargetRevisionSpec() override;
    void CollectStatuses(
        const THashMap<std::string, TWorkerResourceStatusPtr>& workerStatuses,
        const TWorkerResourceStatusPtr& controllerStatus) override;
    NYTree::IMapNodePtr GetView() override;
};

class TMyResource
    : public TResourceBase
{
public:
    using TController = TMyResourceController;
};

YT_FLOW_DEFINE_RESOURCE(TMyResource);
```

Контроллеру, которому нужно переживать рестарты, доступен `Init(initContext)` — доступ к
состоянию, персистируемому вместе с состоянием job manager'а; реализация по умолчанию в
`TResourceControllerBase` ничего не делает.

Обе стороны параметризуются одной секцией `parameters` спецификации ресурса; параметры ресурса
должны расширять параметры контроллера (или совпадать с ними).

### Ревизии

Единица обмена между контроллером и воркерами — **ревизия**: идентификатор плюс произвольное
yson-описание, как её получить. `BuildTargetRevisionSpec()` возвращает только описание; фреймворк
сравнивает его с предыдущим и при изменении назначает новый монотонный `RevisionId`. Доменные
идентификаторы версий (таймстампы, хеши внешнего источника) живут внутри описания, а не в
`RevisionId`.

Вниз едет **целевая** ревизия: она доставляется каждому воркеру вместе с execution spec
(латентность — порядка двух периодов heartbeat) и попадает в ресурс через штатный `Reconfigure`
в поле `TDynamicResourceContext::TargetRevision`. Ресурс, созданный после публикации ревизии —
рестарт воркера, пересоздание менеджера ресурсов — получает её сразу в конструкторе.

Вверх едет состояние инстанса: `IResource::GetRevisionState()` возвращает пару
`{AppliedRevisionId, TargetRevisionId}` — какую ревизию инстанс реально отдаёт и какую целевую
ревизию ему доставили. Применение может отставать от доставки (например, пока файл скачивается):
расхождение полей отличает «ещё не доехало» от «доехало, но ещё переключается». Реализация по
умолчанию в `TResourceBase` считает переключение мгновенным и возвращает оба поля равными
последней доставленной ревизии; медленно переключающийся ресурс переопределяет метод.

### Наблюдаемость

`CollectStatuses` получает актуальный срез статусов ресурса по живым воркерам (в том числе
`AppliedRevisionId`) и статус инстанса ресурса на самом контроллере, а `GetView()` возвращает
произвольное состояние контроллера, которое публикуется во flow view под
`/ephemeral_state/resource_controller_views/<resource_id>`. Метрики контроллер пишет
самостоятельно через `Profiler` и `StatusProfiler` своего контекста.

## Файловые ресурсы

`TFileResourceBase<TData>` (`library/cpp/resources/file/file_resource.h`) реализует ресурс с
неизменяемыми данными, которые строятся из версионированного набора файлов. Пользовательский класс
реализует `Initialize`; при необходимости он также переопределяет `Validate`:

```cpp
class TGeobaseResource
    : public TFileResourceBase<TGeobase>
{
protected:
    TGeobasePtr Initialize(const TMaterializedDirectoryPtr& directory) override;
    void Validate(const TGeobasePtr& geobase) override;
};
```

Новая версия проходит последовательность «скачать — инициализировать — проверить — заменить».
Исключение из `Initialize` или `Validate` отклоняет версию и сохраняет предыдущее корректное
состояние. До первой успешной версии `Load` остаётся незавершённым, а `Lock` выбрасывает
исключение.

`Lock()` возвращает `TFileResourceAccessor<TData>`. Accessor фиксирует один snapshot данных и
удерживает относящиеся к нему файлы; переключение ресурса не меняет уже полученный accessor.
Пользователь должен освобождать его как можно раньше.

Изменяемый файловый ресурс нельзя читать из пользовательской логики Swift-вычисления: повтор
эпохи после рестарта может увидеть другую ревизию и нарушить обязательную для Swift
детерминированность. Accessor фиксирует snapshot только в пределах текущей попытки и не решает эту
проблему между попытками. Для изменяемого source используйте `TTransformComputation`, чей вывод
материализуется по эпохам, либо гарантируйте неизменность object id на всё время работы Swift.

Способ получения файла задаётся зарегистрированным `IFileSource`. Реализация обычно наследуется
от `TFileSourceBase`: `Discover()` асинхронно обнаруживает текущую ревизию, а `Download()` полностью
заполняет переданную staging-директорию одним или несколькими файлами и каталогами. Класс
регистрируется макросом `YT_FLOW_DEFINE_FILE_SOURCE`. Source формирует стабильный идентификатор
неизменяемого объекта; равные идентификаторы гарантируют равное содержимое исходных данных.

### Постоянный кеш исходных данных

Воркер сохраняет успешно скачанные исходные данные в постоянном дисковом кеше, настроенном через
`worker.file_storage`. Кеш индексируется по `TFileStorageObjectId`, который вернул file source.
SHA-256 от идентификатора используется только для построения безопасного шардированного пути на
диске; содержимое файлов не хешируется и одинаковые данные с разными идентификаторами не
дедуплицируются. Равные идентификаторы считаются гарантией побайтово одинакового содержимого со
стороны file source.

При cache miss только один конкурентный запрос заполняет объект. Данные сначала записываются в
`staging/<guid>/payload`, после чего Flow проверяет структуру каталога, записывает manifest с
путями, типами и размерами, делает дерево доступным только для чтения и атомарно публикует его
переименованием. Удаление опубликованного объекта тоже начинается с атомарного переименования в
`trash/`; его размер учитывается до фактического удаления. После рестарта незавершённые
staging-каталоги удаляются, корректные опубликованные объекты подхватываются с диска, а удаление
оставшихся trash-каталогов продолжается.

Путь кеша должен быть абсолютным и находиться на томе, который сохраняется в течение заявленного
срока жизни кеша. Значение всегда является точным корнем одного процесса воркера: Flow не добавляет
к нему идентификатор пайплайна, операции или job cookie. Воркер на всё время жизни берёт
неблокирующий эксклюзивный lock на `<path>/.lock`; второй процесс с тем же физическим корнем
завершается при старте с понятной ошибкой. Оставшийся после завершения процесса файл `.lock` не
мешает повторному запуску.

Тестовый или deployment harness обязан передать отдельный точный путь каждому одновременно
работающему воркеру на общей файловой системе. Flow не создаёт постоянный том автоматически.
Приватный sandbox vanilla job изолирует путь, но не гарантирует сохранение кеша после смены
allocation или хоста. Повторное использование возможно только при сохранении того же тома и пути;
иначе происходит обычный cache miss.

Прямыми дочерними элементами корня могут быть только `.lock`, `staging`, `objects` и `trash`.
Неизвестные элементы не удаляются автоматически: они публикуются как ошибка `startup` и блокируют
новые публикации, пока оператор их не удалит или не перенесёт.

Выданный `IFileStorageObject` закрепляет объект: пока существует хотя бы один такой handle, объект
нельзя удалить. После освобождения последнего handle объект становится кандидатом на удаление по
LRU. Кеш не знает о resource id, порядке ревизий и понятии «последняя версия»: все незакреплённые
объекты равноправны. Поэтому он не гарантирует сохранение одной версии выключенного ресурса и не
предпочитает старую ревизию новой.

`soft_size_limit` задаёт целевой суммарный размер управляемых payload-файлов, включая ещё не
удалённый `trash`. Перед публикацией и во время периодической очистки кеш атомарно переносит давно
использованные незакреплённые объекты в `trash` и удаляет их, стараясь вернуться к этому размеру.
`hard_size_limit` ограничивает admission управляемых payload-данных и reservation: если после
фактически завершённого удаления прогнозируемый размер всё ещё превышает лимит, новая публикация
отклоняется.

Оба лимита учитывают размеры обычных файлов внутри опубликованных payload-каталогов и reservation
для выполняющихся скачиваний, размер которых file source сообщил при discovery. Такая загрузка
отклоняется до вызова filler, если reservation не помещается. Загрузки с неизвестным размером
выполняются по одной и проходят окончательную admission-проверку после заполнения staging.

Лимиты не учитывают manifest, каталоги и служебные расходы файловой системы, а неизвестный или
ошибочно заявленный размер нельзя строго ограничить до завершения filler. Поэтому
`hard_size_limit` не является физической квотой тома. При `ENOSPC` текущая попытка завершается
ошибкой и запускает внеплановую очистку; следующую попытку выполняет штатный retry-цикл файлового
ресурса. Если закреплённые объекты занимают больше половины `hard_size_limit`, компонент публикует
предупреждение.

Кешированная директория доступна приложению только для чтения. Распаковка архивов выполняется в
`Initialize()` в отдельное scratch-хранилище, принадлежащее `TData`; менять исходную директорию
нельзя. Пользователь отвечает за наличие системных инструментов, например `tar`. Изменение логики
распаковки повторно запускает `Initialize()` и `Validate()`, но не меняет ключ исходного кеша и не
вызывает повторное скачивание.

Ошибки скачивания, инициализации или проверки сохраняют последнюю корректную версию и повторяются
через `update_retry_period`. Текущая фаза (`Downloading`, `Initializing`, `Validating` или
`WaitingForRetry`) публикуется как `update_state`, а ошибка — в
`/resource_manager/resources/<resource>/file_update`. Ошибки discovery находятся в
`/resource_controllers/<resource>/discovery`. Метрика
`/resource_controller/revision_instance_count` с тегами `revision_id` и `kind=applied|target`
показывает раскатку ревизии. Счётчики hit, miss, ошибок fill, eviction, вытесненных байтов и
отклонённых публикаций, а также gauge учтённого размера, `trash`, reservation, количества объектов
и закреплённых данных находятся под `/file_storage`. Там же публикуются отдельные ошибки
`capacity`, `disk_full`, `pinned_overuse` и `startup`.

### Неизменяемый локальный файл

`TLocalFileSource` предназначен для примеров, тестов и окружений, где один абсолютный путь
указывает на одинаковый неизменяемый файл на каждом воркере. Discovery не делает `stat` и не
читает файл: идентификатор объекта имеет вид `local_file:v1:<path>`.
Замена файла на месте нарушает контракт; новую версию нужно публиковать под новым путём.

```yson
file_source = {
    file_source_class_name = "NYT::NFlow::TLocalFileSource";
    parameters = {
        path = "/absolute/path/visible/to/every/worker/data.bin";
    };
};
```

При скачивании файл копируется в корень материализованной директории под исходным basename.

### Обновляемый YT-файл

`TYTFileSource` отслеживает `id` и `revision` файловой ноды. Кластер можно задать в rich path;
иначе используется кластер пайплайна. Discovery отвергает ноды другого типа, а воркер открывает
файл по object-id и проверяет ревизию reader перед записью блоков в staging. Поэтому перезапись
между discovery и скачиванием не может опубликовать байты под устаревшим идентификатором объекта.
Идентификатор имеет вид `yt_file:v1:<cluster>:<object-id>:<revision>:<basename>`; source для
последнего файла каталога использует тот же формат, поэтому одинаковый YT-файл разделяет кеш.

```yson
file_source = {
    file_source_class_name = "NYT::NFlow::TYTFileSource";
    parameters = {
        path = "<cluster=primary>//path/to/model.bin";
    };
};
```

Перезапись файла на том же пути меняет node revision и после `discover_period` запускает безопасное
переключение ресурса. Период задаётся в динамической конфигурации ресурса и по умолчанию равен
30 секундам.

### Последний файл в YT-каталоге

`TYTDirectoryLastFileSource` просматривает только непосредственных детей каталога, отбрасывает
ноды не типа `file` и выбирает лексикографически наибольшее имя. Пустой каталог не публикует
ревизию; после предыдущего успеха контроллер продолжает держать последнюю цель. Скачивание
выбранного файла использует ту же проверку object-id и node revision, что и `TYTFileSource`.

```yson
file_source = {
    file_source_class_name = "NYT::NFlow::TYTDirectoryLastFileSource";
    parameters = {
        path = "<cluster=primary>//path/to/releases";
    };
};
```

Для монотонной раскатки имена файлов должны иметь лексикографически сортируемый формат, например
`000001`, `000002`.
