# Прямой сабмит SPYT

При прямом сабмите Spark-приложение получает ресурсы от планировщика {{product-name}} без предварительного запуска standalone-кластера. Драйвер координирует приложение, а экзекьюторы выполняют его задачи.

Ниже описаны принцип работы и настройки прямого сабмита. Порядок запуска приведён в [руководстве](../../../../../user-guide/data-processing/spyt/launch.md#submit).

## Принцип работы { #explanation }

Ключевая идея заключается в том, что Spark делегирует управление ресурсами планировщику {{product-name}}.

### Выделение ресурсов для драйвера { #driver-resources }

- **Cluster mode (Кластерный режим)**: Драйвер также запускается в отдельной Vanilla-операции внутри кластера {{product-name}}. В этом режиме жизненный цикл драйвера (включая логирование, мониторинг и перезапуск при сбоях) полностью контролируется YTsaurus. Подходит для production задач.
- **Client mode (Клиентский режим)**: Драйвер запускается на клиентском хосте — например, на локальной машине разработчика или в Jupyter-ноутбуке. Этот режим удобен для отладки и интерактивной работы, так как обеспечивает прямой доступ к логам и состоянию драйвера.

  {% note warning "Внимание" %}

  В клиентском режиме должен быть обеспечен сетевой доступ между экзекьюторами и драйвером.

  {% endnote %}

### Выделение ресурсов для экзекьюторов { #executor-resources }

В данном режиме планировщик выделяют ресурсы экзекьюторам напрямую в рамках отдельной Vanilla операции на кластере {{product-name}}. Джоба в составе операции соответствует одному экзекьютору Spark. Спецификация экзекьюторов (количество CPU, объем памяти, тип диска и т.п.) описаны в разделе Task в спецификации операции. Возможно описание разных профилей ресурсов для экзекьюторов Spark для задач с неоднородной нагрузкой в течение жизенного цикла.

## Преимущества подхода { #advantages }

- **Эффективное использование ресурсов** — выделение по требованию, минимум простоя.
- **Простое управление** — единый уровень контроля вместо дублирования (YTsaurus + Standalone).
- **Гибкость** — работа без потерь при низкой загрузке.
- **Быстрый старт задач** — нет нужды предварительно поднимать кластер.
- **Лёгкая миграция** — совместимость с другими кластерами (включая Hadoop) за счёт стандартного SparkAPI.

## Конфигурирование {{product-name}} операции  { #operation-config }

Помимо стандартных параметров Spark для драйвера и экзекьюторов дополнительно можно конфигурировать операции и таски через соответствующие conf параметры `spark.ytsaurus.{driver|executor}.{operation|task}.parameters`. В качестве значения указывается yson-строка с допустимыми параметрами ванила операции. Например, можно задать тип и объем подключаемых дисков:
```bash
--conf spark.ytsaurus.executor.task.parameters='{"disk_request"={"disk_space"=1234567;
                                                 "account"="disk_account_name";
                                                 "medium_name"="ssd_slots_physical";};
                                                }'
```
Полный список параметров можно посмотреть в разделе [опции операции](../../../../../user-guide/data-processing/operations/operations-options.md).

## Использование Docker-образов и Porto-слоёв { #images }

При прямом сабмите Spark-приложений в {{product-name}} для задач драйвера и экзекьюторов можно использовать как Docker-образы, так и Porto-слои. Это позволяет подготовить окружение выполнения с нужными системными библиотеками, Python-пакетами и другими зависимостями.

Информацию о сборке собственного Docker-образа можно найти в [разделе про конфигурирование кластера](../../../../../user-guide/data-processing/spyt/cluster/configuration.md#build-image).

Передача Docker-образа или Porto-слоёв выполняется через дополнительные параметры:

```bash
OP_SPEC='{"docker_image"="[REGISTRY/]IMAGE:TAG";}'

spark-submit --master "ytsaurus://<cluster-host>:<port>" \
             --deploy-mode cluster \
             --num-executors 1 \
             --queue <pool> \
             --conf spark.ytsaurus.executor.task.parameters="$OP_SPEC" \
             --conf spark.ytsaurus.driver.task.parameters="$OP_SPEC" \
             ./spark-job.py
```

Подробнее можно прочитать в разделе [образы корневой файловой системы](../../../../../user-guide/data-processing/layers/layer-paths.md).

## Роли RPC-прокси { #proxy-roles }

[Роль прокси](../../../../../admin-guide/cluster-access-proxy/index.md#proxy-role) — строковая метка для выбора группы RPC-прокси при [обнаружении прокси](../../../../../admin-guide/cluster-access-proxy/index.md#discovery-roles) (discovery). Разные роли позволяют разделить подключения с клиентского хоста и из джобов кластера {{product-name}}.

Один процесс может использовать несколько клиентов {{product-name}}: для управления операциями и для работы с данными. Способ подключения зависит от назначения клиента:

#|
|| **Процесс** | **Назначение клиента** | **Подключение** ||
|| `spark-submit`, `spark-shell` или драйвер в режиме `client` на клиентском хосте | Отправка приложения, чтение конфигураций SPYT и управление операциями | Discovery ||
|| Драйвер в режиме `client` на клиентском хосте без локального job-сокета | Чтение и запись данных | Discovery ||
|| Драйвер в режиме `cluster` | Управление операциями экзекьюторов | Discovery ||
|| Драйвер и экзекьюторы в джобах {{product-name}} | Чтение и запись данных | Локальный job-прокси или discovery — по условиям ниже ||
|#

При доступе к кластеру выполнения клиент данных использует RPC-прокси, встроенную в job-прокси, если `spark.ytsaurus.rpc.job.proxy.enabled=true` (значение по умолчанию) и доступен локальный сокет. Такое подключение обходится без discovery и выбора роли. При чтении данных из другого кластера клиент использует discovery с настроенной ролью, обходя локальный сокет.

Для клиентов с discovery роли задаются двумя параметрами:

- `spark.hadoop.yt.proxyRole` — роль клиента на хосте отправки приложения;
- `spark.hadoop.yt.clusterProxyRole` — отдельная роль для процессов внутри кластера. При подготовке этих процессов она подставляется в `spark.hadoop.yt.proxyRole`. Если отдельная роль не задана, сохраняется клиентская.

Клиент записи через Data Source V1 на экзекьюторе использует сохранённую конфигурацию драйвера; [его ограничение в Spark 3.5.5](#v1-write-proxy-role) описано отдельно. Значения по умолчанию приведены в [справочнике параметров](../../../../../user-guide/data-processing/spyt/thesaurus/configuration.md#proxy-roles), порядок применения настроек — ниже.

Если discovery не может найти подходящие RPC-прокси для роли, обратитесь к [диагностике ошибки Cannot get rpc proxies](../../../../../user-guide/data-processing/spyt/problems.md#cannot-get-rpc-proxies).

## Источники и приоритет конфигурации { #config-sources }

При прямом запуске задач SPYT дополняет `SparkConf` приложения из следующих источников в порядке убывания приоритета:

1. Опции `--conf` команды `spark-submit` и конфигурация `SparkConf` приложения.
1. Секция `spark_conf` конфигурации релиза SPYT. Путь к ней складывается из `spark.ytsaurus.config.releases.path`, версии SPYT и `spark.ytsaurus.config.launch.file` (см. [Опции для запуска задач напрямую](../../../../../user-guide/data-processing/spyt/thesaurus/configuration.md#direct-submit)).
1. Секция `spark_conf` глобальной конфигурации, по умолчанию `//home/spark/conf/global` (параметр `spark.ytsaurus.config.global.path`).

Значения из пользовательской конфигурации не перезаписываются: источники с меньшим приоритетом добавляют только отсутствующие параметры. Исключение — булевы флаги из секции `enablers` конфигураций кластера: они могут только выключить параметр, но не включить.

Этот порядок описывает слияние `SparkConf`. Параметры, прочитанные до слияния, не меняют уже подготовленные настройки запуска. Например, путь `spark.ytsaurus.java.home` считывается до добавления настроек релиза и глобальной конфигурации в `SparkConf`; чтобы изменить Java для запуска драйвера, задайте его через `--conf`.

Клиент, который читает конфигурацию релиза и глобальную конфигурацию, создаётся до их применения. Его роль берётся из `--conf` или `SparkConf`. Поэтому неверная роль только в конфигурации релиза или `//home/spark/conf/global` проявляется позже — в драйвере или экзекьюторах.

### Применение кластерной роли { #cluster-proxy-role }

В режиме `cluster` значение `spark.hadoop.yt.clusterProxyRole` можно задать для всех пользователей в секции `spark_conf` документа `//home/spark/conf/global`: драйвер использует его для запуска экзекьюторов. Пользователь может переопределить значение через `--conf`.

В режиме `client` отдельную роль экзекьюторов задавайте в `--conf` или `SparkConf`. Подстановка `clusterProxyRole` происходит до загрузки конфигурации релиза и глобальной конфигурации, поэтому значение только из этих документов не применяется. Примеры приведены в [руководстве по запуску](../../../../../user-guide/data-processing/spyt/launch.md#proxy-roles-examples).

## Ограничения применения ролей { #proxy-role-limitations }

### Роль при записи через Data Source V1 { #v1-write-proxy-role }

В Spark 3.5.5 при записи через Data Source V1 (`spark.sql.sources.useV1SourceList=yt`) клиент записи на экзекьюторе использует сохранённую Hadoop-конфигурацию драйвера. Она создаётся до подстановки кластерной роли.

Поэтому в режиме `cluster`, если `spark.hadoop.yt.proxyRole=external` задан в `--conf`, а `spark.hadoop.yt.clusterProxyRole=internal` — только в глобальной конфигурации, клиент записи может сохранить роль `external`. При выключенном job-прокси эта роль используется для discovery.

Передайте `--conf spark.hadoop.yt.clusterProxyRole=internal` при отправке приложения: роль будет подставлена до создания Hadoop-конфигурации. Это устраняет описанную причину выбора неверной роли. Доступность прокси и успешность записи зависят также от других настроек и условий.

## Выполнение локальных файлов { #submit-local }

Начиная с версии SPYT 2.4.0 при запуске задач напрямую в {{product-name}} можно указывать локальные файлы в качестве исполняемых модулей и зависимостей без их предварительной загрузки на Кипарис. В этом случае локальные файлы будут предварительно загружены в файловый кеш на Кипарисе и затем будут оттуда использованы в приложении. При повторном запуске будут использоваться уже закешированные файлы. Пример команды `spark-submit` для данного способа приведен ниже:

```bash
spark-submit --master ytsaurus://<cluster name> \
             --deploy-mode cluster \
             --num-executors 5 \
             --executor-cores 4 \
             --py-files ~/path/to/my/dependencies.py \
             ~/path/to/my/script.py
```
