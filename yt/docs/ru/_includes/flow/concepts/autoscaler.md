# Автоскейлер

Автоскейлер подбирает число партиций каждого [Computation](../../../flow/concepts/computation.md). Несколько критериев предлагают свои значения; контроллер выбирает максимальное с учётом задержек и ограничений `min_partition_count` и `max_partition_count`. Явный `desired_partition_count` задаёт число партиций вручную.

## CPU {#cpu}

Критерий CPU увеличивает число партиций, когда их средняя загрузка превышает `desired_average_partition_cpu_load`. Так обработка распределяется между большим числом джобов. При снижении нагрузки рекомендация уменьшается постепенно.

## Throughput {#throughput}

Алгоритм Throughput подбирает число партиций по скорости обработки сообщений. Он помогает `Computation`, которые ждут ответа внешних сервисов и мало используют CPU.

Алгоритм использует две величины:

- **Demand** — требуемая скорость: новый поток плюс скорость догона отставания за заданное время. Поток сообщений от Source, таймеров и Key Visitor пересчитывается для каждого `Computation` через соотношения входных и выходных сообщений в [lineage](../../../flow/concepts/lineage.md). Обычная очередь батчевой обработки исключается из отставания.
- **Capacity** — оценка производительности текущих партиций. Суммарная скорость завершённой обработки `Processed` делится на долю занятого времени самого загруженного джоба. Обе величины усредняются по общему окну; ожидание входа и распределения выхода исключается из занятого времени.

Далее для каждого `Computation` выполняется такой цикл:

1. **Измерение.** Алгоритм собирает статистику со всех текущих джобов за общее окно. Загрузка джобов определяет, насколько надёжно можно сравнивать Capacity до и после изменения числа партиций.
1. **Рост.** Если Demand устойчиво выше Capacity и Computation достаточно нагружен, алгоритм увеличивает число партиций. Шаг зависит от дефицита производительности; для догона отставания он меньше, чем для нового потока.
1. **Сравнение Capacity.** При достаточной загрузке джобов алгоритм сравнивает Capacity с точкой до роста. Если прирост оправдывает увеличение числа партиций, поиск продолжается. Две пробы без достаточного выигрыша означают плато: алгоритм остаётся на большем числе партиций.
1. **Ограниченный поиск.** Если Capacity до и после роста нельзя надёжно сравнить, алгоритм проверяет скорость завершённой обработки Processed. Рост ограничен запасом от исходного числа партиций; подтверждённое увеличение Processed расширяет этот запас. Без прогресса поиск останавливается.
1. **Возврат после ухудшения.** При надёжно измеренном падении Capacity алгоритм возвращается к исходному числу партиций и повторяет измерение с увеличенным окном. Повторяющаяся деградация отображается в статусе Computation.
1. **Уменьшение.** После обработки отставания алгоритм возвращается к началу плато, сохраняя Capacity для Demand и двукратный запас относительно исторического пика штатного спроса. Пик хранится за `peak_demand_window` (по умолчанию — девять дней) и сохраняется при перезапусках; скорость догона в него не входит. Последующие уменьшения также сохраняют запас относительно Processed и выполняются периодически, пачкой по пайплайну. Исторический пик только ограничивает сдутие. Откаты неудачных проб выполняются отдельно.

На неизменном плато алгоритм ждёт подтверждённого улучшения измерений или явного сброса состояния поиска. Другие критерии могут увеличивать число партиций во время прогрева Throughput.

Алгоритм Throughput по умолчанию выключен. Включение: `dynamic_spec.job_manager.partitioning.enable_throughput_autoscaler`. Настройки описаны в [справочнике Throughput](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TThroughputSpec).

## Память таймеров {#timers}

Критерий таймеров увеличивает число партиций, когда среднее число таймеров на партицию превышает `desired_average_partition_timer_count`. Это ограничивает их накопление и расход памяти. Аналогичный критерий учитывает среднее потребление памяти джобов через `desired_average_partition_memory_used`.
