# Порядок обработки сообщений в {{product-name}} Flow

В распределённой потоковой системе строгий глобальный порядок всех сообщений обеспечить непрактично: данные поступают из множества источников, обрабатываются параллельно в разных [партициях](../../../flow/concepts/glossary.md#partition) и [компьютейшенах](../../../flow/concepts/glossary.md#computation). Flow решает эту задачу иначе — через механизм `AlignmentTimestamp`.

Каждое сообщение несёт [AlignmentTimestamp](#alignment-timestamp) — монотонно возрастающую временну́ю метку, которая определяет приоритет обработки:

- **Внутри одного [стрима](../../../flow/concepts/glossary.md#stream)**: сообщения обрабатываются в порядке `(AlignmentTimestamp, message_id)` — полный детерминированный порядок.
- **Между разными [стримами](../../../flow/concepts/glossary.md#stream)**: используется сливающая очередь приоритетов: первыми идут сообщения старше [`stale_input_boost_age`](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TDynamicComputationSpec), затем порядок определяется [приоритетом стрима](#stream-priorities) и далее [StabilizedEventTimestamp](#stabilized-event-timestamp) (вычисляется на основе `AlignmentTimestamp`) с поправкой на [stream_delays](../../../flow/concepts/spec.md#inputordering); при равенстве — по `TaskId`.

Помимо приоритизации существует гарантия порядка для **производных сообщений** — подробнее в разделе [Гарантии порядка](#ordering-guarantees).

## AlignmentTimestamp {#alignment-timestamp}

Помимо [SystemTimestamp и EventTimestamp](../../../flow/concepts/glossary.md#timestamps-and-watermarks), каждое сообщение во Flow несёт поле `AlignmentTimestamp` — временную метку, используемую для выравнивания прогресса обработки между потоками и партициями.

Правила выставления `AlignmentTimestamp`:

- **Сообщения из source-потоков** — равен `WriteTimestamp`, то есть времени записи сообщения в персистентную очередь (например, в QYT{% if audience == "internal" %} или Logbroker{% endif %}).
- **Выходные сообщения `TransformComputation`** — равен `SystemTimestamp` на момент создания сообщения.
- **Во всех остальных случаях** — наследуется от родительских сообщений без изменений.

## StabilizedEventTimestamp {#stabilized-event-timestamp}

`StabilizedEventTimestamp` &mdash; это вычислимый таймстемп, равный `AlignmentTimestamp` + `bias`, где `bias` это средняя разность между `EventTimestamp` и `AlignmentTimestamp` в рамках стрима. `bias` считается на основе тех сообщений стрима, что сейчас находятся в обработке. Используется как неубывающая замена для `EventTimestamp` для приоритезации обработки сообщений из разных стримов.

## Гарантии порядка {#ordering-guarantees}

Порядок сообщений в потоке в общем случае не гарантируется, однако для производных сообщений существует следующая гарантия.

Если во входном потоке сообщение A предшествует сообщению B, и у них есть производные сообщения A' и B' такие, что:

- ключи в их [lineage](../../../flow/concepts/lineage.md) совпадают (то есть [ключи группировки](../../../flow/concepts/glossary.md#key) во всех промежуточных компьютейшенах по пути от источника до текущего компьютейшена одинаковы),
- и в текущем компьютейшене у A' и B' один и тот же ключ,

то A' будет обработано раньше, чем B'.

## Приоритизация партиций внутри одного стрима {#partition-prioritization}

Внутри одного source-стрима партиции приоритизируются по `WriteTimestamp` их сообщений: партиции с более ранними сообщениями обрабатываются в первую очередь. Приоритизация реализована через порядок обработки выходных сообщений в следующих компьютейшенах.

## Приоритизация между стримами {#cross-stream-prioritization}

Между разными стримами первыми обрабатываются сообщения старше [`stale_input_boost_age`](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TDynamicComputationSpec). Далее приоритизация выполняется по [приоритету стрима](#stream-priorities), а при равных приоритетах — по `EventTimestamp`, но опосредованно: фактически упорядочивание происходит по `AlignmentTimestamp` с поправкой, специфичной для каждого стрима, и задержкой из `stream_delays`.

Поправка вычисляется как среднее отличие между `EventTimestamp` и `AlignmentTimestamp` среди сообщений, находящихся в данный момент во всех выходных буферах по данному стриму:

$$ordering\_priority = AlignmentTimestamp + avg(EventTimestamp − AlignmentTimestamp)$$

Такой подход позволяет учитывать специфику каждого стрима (например, систематическую задержку между временем записи в очередь и временем события) и обеспечивает более справедливое межстримовое упорядочивание.

## Приоритеты стримов {#stream-priorities}

Компьютейшен может задать приоритеты своих входных стримов в параметре статической спеки `input_ordering.stream_priorities` — целые числа от -15 до 15. Чем больше значение, тем важнее стрим; у неуказанных стримов приоритет 0. Например, чтобы большой несрочный бэкфилл не мешал обработке актуальных данных:

```yson
input_ordering = {
    stream_priorities = {
        backfill = -1;
    };
};
```

Сообщения разных стримов сравниваются сначала по приоритету стрима и только при равных приоритетах — по `StabilizedEventTimestamp` с задержкой из `stream_delays`. Сообщения менее приоритетного стрима ждут, пока у более приоритетных стримов есть готовые сообщения, если только они не старше `stale_input_boost_age` (по умолчанию 2 часа); такие сообщения обрабатываются первыми. Устаревание определяется приближённо, поэтому некоторые устаревшие сообщения могут ждать дольше этого порога. Свободные ресурсы не простаивают. Приоритет учитывается также при отправке сообщений между джобами и в [распределённом троттлере](../../../flow/concepts/distributed_throttler.md#priority).

### Побочные эффекты {#side-effects}

Пока пониженный стрим ждёт обработки:

- его вотермарк отстаёт, а вместе с ним — вотермарки зависящих от него стримов и [таймеров](../../../flow/concepts/timers.md). Это может включить [выравнивание вотермарков](../../../flow/concepts/spec.md#watermark-alignment);
- его сообщения копятся в буферах. Когда буферы заполнятся, замедлятся компьютейшены, которые пишут этот стрим, а вместе с ними — остальные их выходные стримы и другие подписчики пониженного стрима;
- растут таблицы `input_messages` и `compact_input_messages`: они очищаются по общему для пайплайна вотермарку.

Сообщения старше `stale_input_boost_age` обрабатываются первыми, что сокращает эти эффекты.
