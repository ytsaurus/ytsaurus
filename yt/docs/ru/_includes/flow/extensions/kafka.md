# Kafka-расширение для {{product-name}} Flow

Kafka-расширение читает топики [Apache Kafka](https://kafka.apache.org) и пишет в них через [librdkafka](https://github.com/confluentinc/librdkafka). Оно предоставляет:

- Сорс `NYT::NFlow::TKafkaSource`, который читает партиции топика.
- Асинхронный синк `NYT::NFlow::TKafkaSink`.
- Синхронный синк `NYT::NFlow::TAtLeastOnceKafkaSink`.
- Ресурс `NYT::NFlow::TKafkaClient` с общими для сорса и синков параметрами подключения.

Код расширения находится [здесь]({{source-root}}/yt/yt/flow/extensions/kafka).

## Подключение к Kafka {#client}

Объявите ресурс клиента в разделе `resources` в `Spec`. Kafka-сорсы и синки находят его по идентификатору `KafkaClient`, поэтому ресурс должен называться именно так:

```yson
"resources" = {
    "KafkaClient" = {
        "resource_class_name" = "NYT::NFlow::TKafkaClient";
        "parameters" = {
            "bootstrap_servers" = "kafka-1.example.net:9093,kafka-2.example.net:9093";
            "cluster_name" = "events";
            "security_protocol" = "SASL_SSL";
            "sasl_mechanism" = "SCRAM-SHA-512";
            "sasl_username" = "flow-pipeline";
            "ssl_ca_location" = "/etc/ssl/certs/ca-certificates.crt";
        };
        "dependencies" = {};
    };
};
```

Каждый компьютейшен с Kafka-сорсом или синком указывает этот ресурс в `required_resource_ids` — и для контроллера, и для воркеров:

```yson
"required_resource_ids" = {
    "KafkaClient" = {
        "controller" = %true;
        "worker" = %true;
    };
};
```

Пароль SASL никогда не хранится в `Spec`. Процессы контроллера и воркеров читают его из переменной окружения, имя которой задаёт `sasl_password_env`; по умолчанию это `KAFKA_SASL_PASSWORD`. В Vanilla-операции передайте эту переменную в джобы через `secret_env` — см. [Секреты](../../../flow/devops/vanilla/security.md#secrets). Другие параметры librdkafka, например `compression.type` или `partitioner`, задаются в `extra_config`. Параметры, которыми управляет сам коннектор, например `group.id`, `enable.idempotence` или `bootstrap.servers`, там запрещены.

{% note warning %}

Ключи партиций Kafka-сорсов, а значит, и сохранённые пайплайном оффсеты, строятся из `cluster_name`, а пока оно пустое — из `bootstrap_servers`. Задайте `cluster_name` до смены списка брокеров. Чтобы сохранить ключи работающего пайплайна, сначала задайте в `cluster_name` текущее значение `bootstrap_servers`. Если сменить список брокеров при пустом `cluster_name`, сорсы начнут чтение заново с оффсетов новых ключей.

{% endnote %}

## Чтение из Kafka {#source}

Объявите сорс в разделе `source_streams` компьютейшена-источника, например `NYT::NFlow::TProcessFunctionSourceComputation`:

```yson
"computations" = {
    "reader" = {
        "computation_class_name" = "NYT::NFlow::TProcessFunctionSourceComputation";
        "processing_function" = "TParseEvents";
        "output_stream_ids" = ["events"];
        "required_resource_ids" = {
            "KafkaClient" = {
                "controller" = %true;
                "worker" = %true;
            };
        };
        "source_streams" = {
            "kafka" = {
                "source_class_name" = "NYT::NFlow::TKafkaSource";
                "parameters" = {
                    "topic" = "events";
                    "group_id" = "flow-events";
                };
            };
        };
    };
};
```

Каждую партицию Kafka читает отдельная партиция Flow. Контроллер обновляет число партиций топика раз в `update_partition_count_period`, и новые партиции Kafka становятся новыми партициями сорса. `partition_filter` ограничивает сорс частью партиций.

{% note warning %}

Каждую читаемую партицию обслуживают отдельный librdkafka-консьюмер и отдельный поток. На партицию уходит примерно полтора `max_buffer_bytes` памяти: буфер коннектора и внутренняя очередь librdkafka, ограниченная его половиной. Планируйте память и число воркеров по числу партиций.

{% endnote %}

Сорс выдаёт по одному сообщению Flow на каждую запись (record) Kafka. Колонки сообщения:

#|
|| **Колонка** | **Тип** | **Содержимое** ||
|| `data` | `string` | Значение записи. Null для записи с null-значением — в компактифицируемом топике это tombstone, — а также для записи, сохранённой политикой `malformed_message_policy = keep`. ||
|| `key` | `string` | Ключ записи. Null для записи без ключа. ||
|| `unparsed` | `any` | Для записи, сохранённой политикой `malformed_message_policy = keep`, — YSON-словарь `{data = <значение записи>}`, где значение записи передаётся как есть, без распаковки. В остальных случаях null. ||
|| `partition` | `int64` | Номер партиции Kafka, в которой находится запись. ||
|| `offset` | `int64` | Оффсет записи. ||
|| `sub_offset` | `int64` | Номер сообщения внутри записи. У `TKafkaSource`, который выдаёт по одному сообщению на запись, всегда 0; производные сорсы могут разбивать запись на несколько сообщений. ||
|| `timestamp` | `int64` | Временная метка записи в секундах. ||
|#

### Оффсеты и группа консьюмеров {#source-offsets}

Сорс хранит позицию чтения в стейте пайплайна: оффсет каждой партиции сохраняется в каждой эпохе, и после рестарта сорс продолжает чтение с него. Группа консьюмеров `group_id` не распределяет партиции. Сорс по возможности коммитит в неё сохранённые оффсеты, чтобы стандартные инструменты Kafka, например `kafka-consumer-groups`, показывали лаг пайплайна.

Если включён `use_consumer_group_offset` (по умолчанию включён), закоммиченный оффсет группы может сдвинуть партицию вперёд. При старте партиции сорс сравнивает оффсет группы с сохранённым:

- Оффсет группы, опережающий сохранённый, принимается, а записи между ними пропускаются. Так оператор сдвигает партицию при остановленном пайплайне, например командой `kafka-consumer-groups --reset-offsets --to-latest`.
- Оффсет группы, отстающий от сохранённого, игнорируется: так партицию назад не сдвинуть. Чтобы перечитать уже прочитанные записи, сбросьте позицию чтения — см. [Сброс позиции чтения](#source-reset).
- Оффсет группы за концом партиции останавливает партицию до сброса оффсета группы.

Выключите `use_consumer_group_offset`, если группу используют несколько пайплайнов или другие консьюмеры.

### Удалённые и пересозданные данные {#source-retention}

Записи, удалённые по retention до того, как сорс их прочитал, пропускаются: сорс продолжает чтение с самого раннего доступного оффсета.

Пересоздание или усечение топика под тем же именем сорс замечает, только если видит, что последний оффсет партиции меньше оффсета, до которого пайплайн уже дочитал. Последний оффсет сорс проверяет раз в `watermark_update_period`. Заметив такое, сорс останавливает чтение партиции с ошибкой, а не читает новый топик с неверной позиции. Пока партиция остановлена, сенсор `/status_profiler/broken{path="/sources/<source_stream>/topic_identity"}` равен `1`, где `<source_stream>` — имя сорса в `source_streams`; на этот сенсор можно настроить алерт.

Если новый топик до проверки успел накопить не меньше записей, чем пайплайн уже прочитал из старого, сорс пересоздания не заметит: он продолжит чтение с сохранённого оффсета и пропустит начало нового топика. Поэтому после пересоздания топика сразу сбросьте позицию чтения, не дожидаясь ошибки.

### Сброс позиции чтения {#source-reset}

Чтобы перечитать записи или восстановить партиции после пересоздания топика, сбросьте оффсеты, которые сорс хранит в стейте пайплайна. Процедура ниже рассчитана на `TProcessFunctionSourceComputation` и требует успешной остановки пайплайна через drain.

Если после утраты данных топика drain не может дочитать ранее опубликованные сообщения, поставьте старый пайплайн на паузу и создайте новый с отдельным `group_id`. Пайплайн в состоянии `Completed` также нельзя запустить повторно: для нового чтения нужен новый пайплайн.

1. Остановите пайплайн и дождитесь состояния `Stopped`.
2. Командой `read-states` из [Flow CLI](../../../flow/tools/cli.md) прочитайте состояния с фильтрами `--computation-id <компьютейшен с сорсом>`, `--target key_state` и `--name '/$active_source/v0'`. Задайте `--limit`, достаточный для всех нужных партиций: по умолчанию возвращается не более 10 строк. Для `TProcessFunctionSourceComputation` именно в них хранятся оффсеты. В секции `key_states` выберите нужные партиции по `key`: первый элемент ключа — имя сорса в `source_streams`, последний — номер партиции Kafka.
3. Для каждого выбранного полного `key` выполните `delete-states` с теми же `--computation-id`, `--target` и `--name` и добавьте фильтр `--key` с полным значением из `read-states`. Без `--commit` команда только подсчитывает строки, которые удалит. Убедитесь, что найдена одна строка в `matched_states.key_states` и ни одной в остальных секциях, затем повторите с `--commit`. Не удаляйте остальные состояния компьютейшена: у других сорсов имя состояния может совпадать.
4. Если включён `use_consumer_group_offset`, переставьте оффсеты группы `group_id` туда, откуда нужно начать чтение, например на начало партиций командой `kafka-consumer-groups --reset-offsets --to-earliest` (см. [документацию Kafka](https://kafka.apache.org/43/operations/basic-kafka-operations/#managing-consumer-groups)). Иначе сорс вернётся к оффсетам, которые закоммитил последними.
5. Запустите пайплайн и проверьте позицию чтения по колонкам `partition` и `offset` выходных сообщений сорса. Партиция без сохранённого оффсета начинает чтение с оффсета группы, если он задан и его использование включено, а иначе — с самого раннего доступного оффсета.

### Конечное чтение {#source-finite}

При `finite = %true` сорс завершает поток, когда догоняет текущий конец партиций. Это не снимок топика на момент запуска: сорс может прочитать и более поздние записи. Если продюсеры постоянно добавляют данные, чтение может не завершиться.

## Запись в Kafka {#sinks}

Оба синка принимают один входной поток. Байты колонки `payload_column` становятся значением записи, а значение null записывается как null-значение Kafka — в компактифицируемом топике это tombstone. Необязательная колонка `key_column` задаёт ключ записи; librdkafka распределяет записи без ключа по партициям. `message_id_header` добавляет заголовок с идентификатором сообщения Flow; ограничения дедупликации описаны в разделе [At-least-once](#at-least-once).

#|
|| **Синк** | **Как пишет** | **Гарантия** ||
|| `NYT::NFlow::TKafkaSink` | Асинхронно: после коммита эпохи. | По умолчанию exactly-once, с `delivery_guarantee = at_least_once` — at-least-once. ||
|| `NYT::NFlow::TAtLeastOnceKafkaSink` | Синхронно: каждая эпоха ждёт, пока Kafka подтвердит её записи. | At-least-once. ||
|#

Объявите синк в разделе `sinks` компьютейшена, который выдаёт записываемый поток. Например:

```yson
"computations" = {
    "<computation>" = {
        "required_resource_ids" = {
            "KafkaClient" = {
                "controller" = %true;
                "worker" = %true;
            };
        };
        "sinks" = {
            "kafka" = {
                "sink_class_name" = "NYT::NFlow::TKafkaSink";
                "input_stream_ids" = ["results"];
                "parameters" = {
                    "topic" = "results";
                    "payload_column" = "value";
                    "key_column" = "key";
                    "message_id_header" = "flow-message-id";
                };
            };
        };
    };
};
```

{% note info %}

Коннектор сохраняет партиционер librdkafka по умолчанию — `consistent_random` (CRC32), без специальных преимуществ для Flow. Java-клиент использует murmur2, поэтому одинаковые ключи могут попасть в разные партиции. Для совместимости с Java-продюсерами задайте `"partitioner" = "murmur2_random"` в `extra_config` ресурса клиента.

{% endnote %}

## Гарантии доставки {#guarantees}

### At-least-once {#at-least-once}

`TAtLeastOnceKafkaSink` и `TKafkaSink` с `delivery_guarantee = at_least_once` используют идемпотентного продюсера: повторы отбрасываются только в пределах одной его сессии. После сбоя джоб перезапускается и повторяет неподтверждённую запись, поэтому в Kafka возможны дубликаты.

Заголовок, имя которого задано в `message_id_header`, содержит идентификатор сообщения Flow. Возможность дедупликации по нему зависит от того, как сообщение повторно попало в синк:

- Асинхронный `TKafkaSink` повторно отправляет сообщения закоммиченных эпох с прежними идентификаторами. У Transform вывод сохранён в `output_messages`, а Swift восстанавливает его вычислением и должен соблюдать [требования к детерминизму](../../../flow/concepts/guarantees.md#determinism). Консьюмер может отбрасывать такие повторы по заголовку.
- Синхронный `TAtLeastOnceKafkaSink` может записать сообщение до неудавшегося коммита эпохи. При повторном вычислении Transform-компьютейшен может выдать тому же результату новый идентификатор, поэтому заголовок не гарантирует дедупликацию. Для этого сценария передавайте в содержимом сообщения стабильный прикладной идентификатор и используйте его на стороне консьюмера.

### Exactly-once {#exactly-once}

По умолчанию синк `TKafkaSink` доставляет сообщения exactly-once. Для этого нужны поддержка транзакций на брокерах, дополнительные права и настройка консьюмеров — см. требования ниже. Если выполнить их нельзя, задайте `delivery_guarantee = at_least_once`.

В режиме exactly-once синк пишет записи в транзакциях Kafka:

1. Каждая партиция синка получает transactional ID: `transactional_id_prefix`, за которым следует producer ID партиции. Producer ID сохраняется в стейте синка и не меняется при рестартах.
2. При старте партиция синка отстраняет (fence) писателей своих прошлых сессий и прерывает оставленную ими открытую транзакцию. Устаревший джоб, который после этого пытается писать, завершается с ошибкой.
3. Каждая транзакция пишет пачку записей вместе с маркером прогресса — оффсетом группы консьюмеров с тем же именем, что и transactional ID, в партиции 0 топика. Оффсет маркера — порядковый номер последнего сообщения, записанного транзакцией; синк нумерует сообщения партиции подряд.
4. Flow считает сообщения доставленными только после коммита их транзакции. После рестарта синк читает маркер и пропускает повторно отправленные сообщения, которые уже закоммичены.

Требования:

- Консьюмеры должны читать с `isolation.level = read_committed`, иначе они видят и записи прерванных транзакций. librdkafka по умолчанию использует `read_committed`, но многие другие клиенты, в том числе Java-клиент, по умолчанию используют `read_uncommitted`.
- Брокеры должны поддерживать транзакции, а их `transaction.max.timeout.ms` должен быть не меньше `transaction_timeout`.
- Пользователю Kafka, от имени которого подключается синк, нужны следующие права. Права на первые два ресурса выдайте через префиксные ACL на transactional ID и группы консьюмеров, имена которых начинаются с `transactional_id_prefix`.

  #|
  || **Ресурс** | **Операции** ||
  || Transactional ID с префиксом `transactional_id_prefix` | `Write`, `Describe` ||
  || Группы консьюмеров с префиксом `transactional_id_prefix` | `Read` ||
  || Топик | `Write`, `Describe`, `Read` ||
  |#

- Не удаляйте группы маркеров и не сбрасывайте их оффсеты.
- После рестарта Flow должен передать синку те же сообщения в том же порядке, потому что маркер определяет сообщения по их порядковым номерам. Flow обеспечивает это, если предшествующие компьютейшены соблюдают [требования к детерминизму](../../../flow/concepts/guarantees.md#determinism).

Транзакция пишет не больше `max_transaction_record_count` записей и `max_transaction_byte_size` байтов. Исключение — запись, которая сама больше `max_transaction_byte_size`: синк пишет её в отдельной транзакции.

Ошибки синк обрабатывает в зависимости от их вида:

- Повторяемую ошибку запроса к Kafka синк повторяет, не прерывая транзакцию, — до десяти попыток подряд.
- Если после ошибки транзакцию нужно прервать, синк прерывает её и снова пишет те же записи пачкой вдвое меньшего размера. После десяти таких ошибок подряд синк завершает джоб с ошибкой.
- Фатальная ошибка сразу завершает джоб с ошибкой. Например, так бывает, когда продюсер отклоняет запись больше своего `message.max.bytes` или когда писателя отстранила более новая сессия.

Перезапущенный джоб восстанавливается по маркеру. Поэтому запись, которую отклоняет продюсер или брокер, будет снова и снова приводить к ошибке джоба, пока не изменится ограничение или запись.

Меняйте `delivery_guarantee` и `transactional_id_prefix` только при остановленном пайплайне. Когда синк переключается с `at_least_once` на `exactly_once`, сообщения, доставка которых не была подтверждена в момент переключения, могут быть записаны дважды.

### Потеря маркера прогресса {#lost-marker}

Маркер теряется, когда истекает срок хранения оффсета его группы консьюмеров — если в течение `offsets.retention.minutes` брокера (по умолчанию 7 дней) не было коммитов, — а также когда группа удалена или её оффсет сброшен. После этого синк не может определить, какие из неподтверждённых пайплайном сообщений уже есть в Kafka.

Если такие сообщения, возможно, есть, партиция синка отказывается стартовать с ошибкой `Kafka sink progress marker cannot be trusted`, и её джоб раз за разом перезапускается, ничего не записывая. Это происходит, только если одновременно партиция синка остановилась с неподтверждёнными сообщениями, например после сбоя, а маркер был потерян до её повторного старта. Штатная остановка пайплайна не оставляет неподтверждённых сообщений, а партиция синка без них стартует и без маркера.

Чтобы продолжить, примите, что эти сообщения будут записаны повторно и могут продублироваться: задайте динамический параметр `allow_missing_progress_marker` со значением `%true` в `DynamicSpec` по пути `computations/<computation>/sinks/<sink>/parameters`. Параметр читается при старте партиции синка, и партиции с ошибкой перезапускаются сами. Когда пайплайн восстановится, верните значение `%false`.

Если ожидаются долгие остановки пайплайна, увеличьте `offsets.retention.minutes` брокера так, чтобы значение превышало их длительность.

## Диагностика ошибок {#troubleshooting}

#|
|| **Текст ошибки** | **Причина и исправление** ||
|| `The "extra_config" key "<key>" is managed by the connector and cannot be overridden` | В `extra_config` задан параметр, которым управляет коннектор. Уберите его из `extra_config` и используйте соответствующий параметр ресурса, если он есть. ||
|| `Kafka metadata request for topic "<topic>" failed` | Топик не существует, или у пользователя Kafka, от имени которого подключается клиент, нет права `Describe` на него. Создайте топик или выдайте право. ||
|| `Kafka consumer group offset is beyond the topic end; reset the group offsets to restart the partition` | Закоммиченный оффсет группы `group_id` находится за концом партиции, например после пересоздания топика. Переставьте оффсеты группы командой `kafka-consumer-groups --reset-offsets` (см. [документацию Kafka](https://kafka.apache.org/43/operations/basic-kafka-operations/#managing-consumer-groups)) или выключите `use_consumer_group_offset`. ||
|| `Kafka high watermark is below the persisted offset; was the topic recreated?` | Топик пересоздан или усечён под тем же именем, и сорс остановил чтение партиции. Сбросьте позицию чтения — см. [Сброс позиции чтения](#source-reset). ||
|| `Kafka sink progress marker cannot be trusted` | Маркер прогресса партиции exactly-once-синка отсутствует, сброшен или не согласуется со стейтом пайплайна, а неподтверждённые сообщения могут быть уже закоммичены. См. [Потеря маркера прогресса](#lost-marker). ||
|| `Kafka transaction failed` с `Message size too large` | Запись превышает ограничение на размер сообщения. Если в ошибке есть `Failed to produce Kafka message`, запись отклонил продюсер: увеличьте `message.max.bytes` в `extra_config` ресурса клиента (по умолчанию 1000000 байтов). Иначе запись отклонил брокер: увеличьте `max.message.bytes` топика. Размер записи должен укладываться в оба ограничения. Можно также уменьшить размер записей. ||
|| `This instance has been fenced by a newer instance` | Устаревший джоб партиции exactly-once-синка попытался писать после старта заменившего его джоба. Действий не требуется. ||
|#
