# Работа с YDB в {{product-name}} Flow

YDB-расширение читает сообщения из топиков и записывает в них результаты пайплайна. Для обычного топика задайте адрес сервера, базу и путь топика явно. Для чтения также нужен заранее созданный консьюмер. Учётная запись должна иметь права на чтение или запись соответствующего топика.

Классы расширения находятся в пространстве имён `NYT::NFlow`. [Исходный код]({{source-root}}/yt/yt/flow/extensions/ydb) содержит коннекторы, ресурс драйвера и вспомогательные функции C++ и Python.

В `flow_server`, собранном из этих исходников, классы уже зарегистрированы. При сборке собственного C++-бинарного файла через `ya` добавьте зависимость:

```text
PEERDIR(yt/yt/flow/extensions/ydb/cpp)
```

В старых выпусках сервера этих классов может не быть. Публичного интерфейса YQL для этих коннекторов нет.

## Требования к соединению {#transport}

Встроенный `TYdbTopicDriver` передаёт данные без шифрования. В `endpoint` укажите `host:port`, например `localhost:2135`. В ресурсе нет настроек TLS, сертификата CA или клиентского сертификата. Префикс `grpcs://` не включает TLS в этом драйвере: ресурс не может напрямую подключиться к серверу, принимающему только TLS-соединения.

Аутентификация по токену или логину и паролю не шифрует соединение. Не передавайте токены и пароли по недоверенной сети без шифрования.

## Подготовка топиков {#prerequisites}

Сервер должен поддерживать сессии чтения Topic API с привязкой к отдельным партициям. Для автоматического разделения партиций также нужны сведения о связях родительских и дочерних партиций и события завершения партиций. Учётной записи Flow нужно право `SELECT ROW` на входной топик.

Установите YDB CLI и настройте профиль подключения и аутентификации `flow` по [инструкции YDB CLI](https://ydb.tech/docs/ru/reference/ydb-cli/connect). Выберите ту же базу, что и в спецификации Flow. Настройки соединения CLI независимы: TLS в CLI не включает TLS в ресурсе Flow.

Для подготовки используйте учётную запись с правами на создание топиков и добавление консьюмеров. Для примеров ниже [создайте топики](https://ydb.tech/docs/ru/reference/ydb-cli/topic-create) и [добавьте консьюмеров](https://ydb.tech/docs/ru/reference/ydb-cli/topic-consumer-add):

```bash
ydb --profile flow topic create events --supported-codecs raw,gzip,zstd
ydb --profile flow topic consumer add events --consumer flow-reader --supported-codecs raw,gzip,zstd
ydb --profile flow topic create processed-events --supported-codecs raw,gzip,zstd
ydb --profile flow topic consumer add processed-events --consumer flow-check --supported-codecs raw,gzip,zstd
```

Используйте новые имена топиков или подставьте существующие топики и консьюмеров с нужными правами и кодеками. Отдельный консьюмер `flow-check` нужен для проверки результата. Новый консьюмер без начальной временной метки читает с самого старого сообщения, которое ещё хранится в топике.

## Подключение драйвера {#driver}

Ресурс `NYT::NFlow::TYdbTopicDriver` создаёт клиентов YDB. Объявите его в `Spec.resources`. Разные ресурсы позволяют читать и писать с разными учётными данными:

```yson
resources = {
    ReadYdb = {
        resource_class_name = "NYT::NFlow::TYdbTopicDriver";
        parameters = {
            auth_mode = "login";
            username = "flow-reader";
            password_env_var = "FLOW_READ_PASSWORD";
        };
        dependencies = {};
    };
    WriteYdb = {
        resource_class_name = "NYT::NFlow::TYdbTopicDriver";
        parameters = {
            auth_mode = "token";
            token_env_var = "FLOW_WRITE_TOKEN";
        };
        dependencies = {};
    };
};
```

В каждом компьютейшене с коннектором укажите ресурс в `required_resource_ids`. Внешний ключ — имя ресурса в `Spec.resources`, а `alias = "YdbDriver"` — имя, по которому коннектор находит ресурс внутри компьютейшена. Контроллер и воркер получают ресурсы независимо; для YDB-коннекторов включите оба флага:

```yson
required_resource_ids = {
    ReadYdb = {
        alias = "YdbDriver";
        controller = %true;
        worker = %true;
    };
};
```

Этот фрагмент относится к читающему компьютейшену. Для пишущего используйте ключ `WriteYdb` с тем же локальным псевдонимом `YdbDriver`. Если глобальный ресурс уже называется `YdbDriver`, псевдоним можно не задавать. Общие правила описаны в разделе [Ресурсы](../../../flow/cpp/resources.md).

Настройки драйвера и значения по умолчанию: [`TYdbTopicDriverConfig`](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TYdbTopicDriverConfig).

### Аутентификация {#authentication}

Параметры `token_env_var` и `password_env_var` содержат **имена переменных окружения**, а не токен или пароль.

#|
|| **`auth_mode`** | **Выбор учётных данных** ||
|| `auto` — по умолчанию | Токен из `token_env_var` (по умолчанию `YDB_TOKEN`); если переменная пуста, аутентификация отключена. ||
|| `token` | Токен из `token_env_var`; пустое значение вызывает ошибку. ||
|| `login` | Обязательные `username` и `password_env_var`. Пароль читается только из указанной переменной; пустое значение вызывает ошибку. ||
|| `anonymous` | Аутентификация отключена; токен и пароль из окружения не читаются. ||
|#

В C++ конструктор `TYdbTopicDriver` также принимает `std::shared_ptr<NYdb::ICredentialsProviderFactory>`. Переданная фабрика имеет приоритет над выбором учётных данных из конфигурации и окружения.

Для Vanilla-операции перечислите имена секретных переменных в `vanilla.secret_env` конфигурации запуска:

```yson
vanilla = {
    secret_env = ["FLOW_READ_PASSWORD"; "FLOW_WRITE_TOKEN";];
};
```

До запуска или реанимации операции задайте непустые значения этих переменных в окружении запускающего процесса. Он передаст их через secure vault, а процессы узлов восстановят переменные окружения. Значения секретов не записывайте в `Spec`. См. [Секреты](../../../flow/devops/vanilla/security.md#secrets).

## Чтение топика {#source}

Выберите класс сорса по устройству одного сообщения YDB:

#|
|| **Класс** | **Результат** ||
|| `NYT::NFlow::TYdbSource` | Одно сообщение YDB становится одним сообщением Flow после декомпрессии. ||
|| `NYT::NFlow::TYdbMultiLineSource` | Сообщение разделяется по `row_delimiter`, по умолчанию `\n`. ||
|| `NYT::NFlow::TYdbFramingSource` | Сообщение разбирается на фреймы; `framing_format` по умолчанию `auto`. ||
|#

Добавьте сорс в `source_streams` компьютейшена-источника. Ниже — фрагмент этого раздела для обычного топика:

```yson
source_streams = {
    events = {
        source_class_name = "NYT::NFlow::TYdbSource";
        parameters = {
            endpoint = "localhost:2135";
            database = "/Root";
            topic = "events";
            consumer = "flow-reader";
            attributes_column = "topic_attributes";
        };
    };
};
```

Замените `endpoint`, `database`, `topic` и `consumer` значениями своего подключения. Все четыре поля обязательны; настройки драйвера не заменяют адрес топика. Компьютейшену также нужна привязка ресурса из раздела [Подключение драйвера](#driver).

Для проверки чтения отправьте известное сообщение в `events` и убедитесь, что на выходе сорса его байты находятся в `data`, а оффсет в топике — в `offset`.

Сорс выдаёт колонки:

- `data` (`string`) — данные выходного сообщения;
- `unparsed` (`any`) — YSON-представление повреждённого сообщения при политике `keep`;
- `offset` (`int64`) — оффсет исходного сообщения YDB;
- `sub_offset` (`int64`) — номер сообщения внутри результата разбиения, начиная с нуля.

Опциональный `attributes_column` добавляет YSON-колонку с пользовательскими атрибутами. Её имя не должно совпадать с `data`, `unparsed`, `offset` или `sub_offset`. Служебные атрибуты Flow и зарезервированные имена YDB скрыты, кроме `__key`, который содержит Kafka key.

В `DynamicSpec.computations/<computation>/source_streams/<source>/parameters` задаются `read_from_instant`, `max_time_lag` и `malformed_message_policy`. Политика по умолчанию `fail` останавливает обработку повреждённого сообщения с ошибкой; `drop` пропускает его, а `keep` сохраняет в `unparsed`. Для framing согласуйте формат с отправителем: `auto` не определяет `light_protoseq` и может ошибиться на неоднозначном начале `lenval`. См. [Библиотека framing](../../../flow/extensions/framing.md).

Параметры и значения по умолчанию:

- `TYdbSource`: [статические](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TUnitedParameters_NYT_NFlow_TYdbSource), [динамические](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TDynamicUnitedParameters_NYT_NFlow_TYdbSource).
- `TYdbMultiLineSource`: [статические](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TUnitedParameters_NYT_NFlow_TYdbMultiLineSource), [динамические](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TDynamicUnitedParameters_NYT_NFlow_TYdbMultiLineSource).
- `TYdbFramingSource`: [статические](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TUnitedParameters_NYT_NFlow_TYdbFramingSource), [динамические](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TDynamicUnitedParameters_NYT_NFlow_TYdbFramingSource).

Параметр `finite` по умолчанию выключен. При `finite = %true` в параметрах сорса чтение может завершиться, когда зафиксированный прогресс достигнет подтверждённых текущих конечных оффсетов партиций. Это наблюдаемые конечные оффсеты, а не снимок, сделанный при запуске. Временное отсутствие сообщений не означает конец данных; непрерывная запись может задерживать завершение.

### Оффсеты и границы восстановления {#source-recovery}

При первом запуске сессия начинает чтение с закоммиченной позиции консьюмера. Чтобы исключить старые сообщения после регистрации консьюмера, перед запуском пайплайна задайте `read_from_instant` в динамических параметрах сорса. Эта временная метка и `max_time_lag` задают дополнительные нижние границы чтения. Они не позволяют вернуться к сообщениям до закоммиченного оффсета консьюмера.

Flow сохраняет прогресс чтения в состоянии пайплайна. Если закоммиченный на сервере оффсет консьюмера опережает этот прогресс, сессия не прочитает сообщения между сохранённой позицией Flow и этим оффсетом. Независимый читатель, который коммитит оффсеты того же консьюмера, может привести к такому пропуску сообщений во Flow. Для таких читателей используйте отдельного консьюмера.

Если при повторном чтении с сохранённой позиции нет прогресса или обнаружен пропуск, Flow может вызвать `DescribePartition` с запросом статистики, чтобы проверить границу хранения данных. Для этого способа восстановления сервер должен поддерживать такой запрос и возвращать в статистике партиции начальный оффсет самых старых данных, которые ещё хранятся в топике. Проверьте, что ваш сервер возвращает эту статистику.

При разделении партиции Flow завершает обработку родительской партиции до состояния `Completed` и только после этого начинает читать дочерние партиции. Flow сохраняет связи между родительскими и дочерними партициями и состояние завершения. Это сохраняет порядок обработки после перезапуска и при повторных разделениях. Если сервер больше не сообщает о родительской партиции, Flow обрабатывает оставшуюся сохранённую работу для неё как для конечной партиции, прежде чем запускать дочерние. Так сохраняется порядок уже сохранённой работы при разделении. Сообщения, удалённые по истечении срока хранения, восстановить нельзя.

Для успешного завершения обработки партиции сохранённый прогресс Flow должен совпадать с закоммиченным оффсетом консьюмера.

### Федерация {#federation}

Федерация топиков YDB позволяет Flow работать с топиками по одному и тому же пути в нескольких именованных кластерах. Для этого нужен сервис обнаружения федерации, который предоставляет администратор развёртывания или поставщик YDB. Порядок настройки сервиса зависит от дистрибутива. Укажите в параметре `endpoint` федеративного сорса или `TYdbTwoPhaseCommitSink` gRPC-адрес, на котором доступен вызов `Ydb.FederationDiscovery.V1.FederationDiscoveryService/ListFederationDatabases`. Сервис должен вернуть успешно завершённую операцию с результатом `ListFederationDatabasesResult`, в поле `federation_databases` которого перечислены именованные кластеры. Если SDK возвращает единственный кластер без имени, коннектор работает в обычном однокластерном режиме. См. [описание сервиса gRPC](https://github.com/ydb-platform/ydb/blob/main/ydb/public/api/grpc/ydb_federation_discovery_v1.proto) и [формат ответа](https://github.com/ydb-platform/ydb/blob/main/ydb/public/api/protos/ydb_federation_discovery.proto).

#### Требования к развёртыванию

- Указывайте для каждого кластера отдельное имя в поле `name` и постоянный уникальный адрес в поле `endpoint`. Поле `path` каждого кластера должно в точности совпадать с параметром `database` коннектора. Контроллеру и воркерам Flow должны быть доступны адрес сервиса обнаружения, адреса кластеров и адреса сервисов YDB, которые кластеры сообщают клиентам. [Требования к незашифрованному соединению](#transport) действуют и для обнаружения, и для подключений к кластерам.
- Сервис обнаружения должен возвращать актуальный статус каждого кластера. Статус `AVAILABLE` разрешает синку с двухфазной фиксацией выбирать кластер для новых записей. При статусах `READ_ONLY` и `UNAVAILABLE` синк не выбирает кластер для новых записей. Flow сохраняет такой кластер в топологии сорса, пока он есть в ответе сервиса обнаружения. Чтение зависит от того, может ли Flow подключиться к кластеру и открыть в нём сессию чтения через Topic API.
- Каждый ресурс `TYdbTopicDriver` использует одни и те же [настройки аутентификации](#authentication) для обнаружения и подключения ко всем кластерам. Проверьте, что сервис обнаружения и каждый кластер принимают заданные учётные данные. В режиме `login` по адресу сервиса обнаружения должен быть доступен и вызов `Ydb.Auth.V1.AuthService/Login`. В каждом кластере учётной записи Flow нужны право `CONNECT` на базу данных и `DESCRIBE SCHEMA` на топик, а также `SELECT ROW` на топики для чтения и `UPDATE ROW` на топики для записи. См. [список прав доступа YDB](https://ydb.tech/docs/ru/yql/reference/syntax/grant).
- Подготовьте каждый топик отдельно во всех кластерах. Для каждого коннектора значение `topic` должно указывать на один и тот же путь в заданной базе данных во всех кластерах. Поддерживайте одинаковое число и схему партиций, в том числе при изменении партиционирования. Для каждого сорса добавьте потокового консьюмера с одним и тем же именем во всех кластерах. Настройте топики и консьюмеров на кодеки, которые используют производители. Выберите срок хранения с учётом ожидаемого отставания чтения и времени простоя. Для синка с двухфазной фиксацией предусмотрите время на завершение отложенных публикаций после восстановления кластера.
- Для `TYdbTwoPhaseCommitSink` включите [отложенную публикацию](#delivery) в каждом кластере, который может принимать запись. Для её операций нужна аутентифицированная учётная запись. При обновлении учётных данных сохраняйте тот же идентификатор владельца (SID), чтобы Flow мог возобновить сохранённую публикацию.

#### Подготовка и проверка кластеров

Например, задайте в сорсе и синке с двухфазной фиксацией `endpoint = "discovery.example.org:2135"` и `database = "/Root/flow"`. Сервис обнаружения по этому адресу возвращает два кластера:

#|
|| **`name`** | **`id`** | **`endpoint`** | **`path`** | **`status`** ||
|| `east` | `flow-east` | `ydb-east.example.org:2135` | `/Root/flow` | `AVAILABLE` ||
|| `west` | `flow-west` | `ydb-west.example.org:2135` | `/Root/flow` | `AVAILABLE` ||
|#

Создайте профили YDB CLI `flow-east` и `flow-west`, как описано в разделе [Подготовка топиков](#prerequisites). В каждом профиле укажите адрес своего кластера и базу `/Root/flow`. В обоих кластерах из-под учётной записи с правами на создание топиков и добавление консьюмеров создайте входной топик `events` с консьюмером Flow `flow-reader` и выходной топик `processed-events` с отдельным консьюмером для проверки `flow-check`. В примере у топиков по две партиции, автоматическое партиционирование выключено, срок хранения сообщений составляет 24 часа. Подберите срок хранения с учётом нагрузки и ограничений обоих кластеров. См. [создание топика](https://ydb.tech/docs/ru/reference/ydb-cli/topic-create) и [добавление консьюмера](https://ydb.tech/docs/ru/reference/ydb-cli/topic-consumer-add).

```bash
for profile in flow-east flow-west; do
    ydb --profile "$profile" topic create --partitions-count 2 --auto-partitioning-strategy disabled \
        --retention-period 24h --supported-codecs raw,gzip,zstd events
    ydb --profile "$profile" topic consumer add --consumer flow-reader --supported-codecs raw,gzip,zstd events
    ydb --profile "$profile" topic create --partitions-count 2 --auto-partitioning-strategy disabled \
        --retention-period 24h --supported-codecs raw,gzip,zstd processed-events
    ydb --profile "$profile" topic consumer add --consumer flow-check --supported-codecs raw,gzip,zstd processed-events
done
```

До запуска пайплайна вызовите `ListFederationDatabases` из сети Flow по описанию сервиса. Тело запроса пустое. Передайте путь базы данных в метаданных `x-ydb-database` и, если включена аутентификация, токен в `x-ydb-auth-ticket`. Для режима `login` используйте токен, полученный при входе. Проверьте, что ответ содержит ожидаемые кластеры, их адреса, путь базы и статусы.

Выполните `ydb --profile flow-east scheme describe events` и повторите проверку для обоих топиков в обоих профилях. Сравните число партиций, кодеки и сроки хранения. Проверьте наличие `flow-reader` в описании `events` и `flow-check` в описании `processed-events` в обоих кластерах. Повторите проверки от имени учётных записей Flow, чтобы подтвердить права на подключение и получение описаний нужных топиков. См. [получение информации об объекте схемы](https://ydb.tech/docs/ru/reference/ydb-cli/commands/scheme-describe).

В тестовом пайплайне задайте `topic = "events"` и `consumer = "flow-reader"` в сорсе и `topic = "processed-events"` в синке. Выполните команду записи из раздела [Примеры и проверка](#examples) с профилем каждого кластера и своим тестовым сообщением. Убедитесь, что Flow прочитал оба сообщения. Для проверки каждой цели записи с двухфазной фиксацией запускайте новый тестовый пайплайн, оставив только этому кластеру статус `AVAILABLE`. Используйте своё тестовое сообщение для каждого запуска. После фиксации эпохи Flow выполните команду чтения с профилем этого кластера и консьюмером `flow-check`. При повторных проверках с этим отдельным консьюмером задайте `--commit true`, чтобы продвигать его оффсет.

#### Чтение и запись

Сорсы читают исходный поток каждого кластера независимо. Flow хранит прогресс чтения по адресу кластера и номеру партиции. Flow не реплицирует топики, не удаляет дубли между кластерами и не синхронизирует оффсеты консьюмеров. Чтобы не обработать одно событие дважды, записывайте его в один кластер или удаляйте дубли в пайплайне.

Обычные синки подключаются к одному развёртыванию YDB через заданный `endpoint` и отправляют данные на адреса его Topic API. Если включить `write_flow_queue_meta`, контроллер также может отправлять служебные сообщения в обнаруженные кластеры. `TYdbTwoPhaseCommitSink` выбирает кластер для новых публикаций через сервис обнаружения. При смене цели Flow может выбрать любой доступный для записи кластер.

Незавершённая публикация остаётся на том адресе и в той базе, где Flow её подготовил, даже если для новых публикаций выбран другой кластер. Если исходный кластер недоступен, публикация может ждать его восстановления. В строгом режиме незавершённая партиция может задержать запуск следующей. При переключении синка сообщения разных эпох могут стать видимыми не по порядку. Если пайплайн допускает такое поведение, задайте `distribution_ordering = "relaxed"` в спецификации компьютейшена. В строгом режиме Flow показывает предупреждение о порядке публикации. Возможность завершить публикацию зависит от доступности исходного кластера и срока хранения данных в нём.

Сохраняйте адреса кластеров постоянными. Если изменить адрес в ответе сервиса обнаружения, ключи партиций сорса изменятся, а незавершённые публикации останутся привязаны к старому адресу. Перед заменой или удалением кластера прекратите отправлять туда новые данные, дочитайте накопившиеся сообщения и завершите публикации, пока адрес ещё доступен. При смене сорса или адреса сервиса обнаружения соблюдайте [правила совместимости сохранённого состояния](#compatibility).

#### Ошибки обнаружения и подключения

- Если вместо именованных кластеров Flow показывает только настроенный `endpoint`, проверьте, вернул ли вызов обнаружения `UNIMPLEMENTED` или `BAD_REQUEST`. Оба ответа могут привести к переходу в однокластерный режим.
- При `Failed to discover topic clusters` проверьте по вложенной ошибке адрес сервиса обнаружения, аутентификацию и наличие кластеров в ответе.
- При `Failed to update cluster info` изучите вложенную ошибку, проверьте адрес кластера, точный путь базы данных, путь топика и право `DESCRIBE SCHEMA`. Если кластеры сообщают разное число партиций, приведите их схему партиционирования в соответствие. Если известные значения расходятся, Flow не может использовать их, чтобы определить число партиций в кластере, который его не сообщил. Если топология кластера неизвестна и число его партиций нельзя ни получить, ни определить по другим кластерам, Flow не может обновить список партиций для всего компьютейшена. Пока список не удаётся обновить, Flow сохраняет текущий набор партиций сорса.
- При `Federation discovery returned no writable cluster` проверьте статусы в ответе сервиса обнаружения, незавершённые публикации и ошибки предыдущих попыток записи. При `UNSUPPORTED` во время отложенной публикации проверьте поддержку этой операции сервером и флаг, который включает её в выбранном кластере.
- При `Topic discovery semantics changed during the sink lifetime` проверьте, не сменился ли список именованных кластеров единственным кластером без имени или наоборот. Восстановите ожидаемый ответ сервиса обнаружения перед возобновлением работы синка.

## Запись в топик {#sink}

Все синки требуют `endpoint`, `database` и `topic`. Из `payload_column` они берут сериализованные байты; по умолчанию колонка называется `data`.

#|
|| **Класс** | **Упаковка и доставка** ||
|| `NYT::NFlow::TYdbSink` | Одно сообщение Flow на сообщение YDB; асинхронная доставка через `output_messages`. ||
|| `NYT::NFlow::TYdbFramingSink` | Несколько сообщений Flow в одном framing-блоке; асинхронная доставка через `output_messages`. ||
|| `NYT::NFlow::TYdbTwoPhaseCommitSink` | Отложенная публикация после фиксации эпохи; требует поддержки сервера. Опциональный `framing_format` включает упаковку. ||
|| `NYT::NFlow::TYdbAtLeastOnceSink` | Прямая запись отдельных сообщений; at least once. ||
|| `NYT::NFlow::TYdbAtLeastOnceFramingSink` | Прямая запись framing-блоков; at least once. ||
|#

Например, фрагмент `sinks` пишущего компьютейшена:

```yson
sinks = {
    ydb = {
        sink_class_name = "NYT::NFlow::TYdbSink";
        input_stream_ids = ["events";];
        parameters = {
            endpoint = "localhost:2135";
            database = "/Root";
            topic = "processed-events";
            payload_column = "data";
        };
    };
};
```

Поток `events` должен существовать в пайплайне и содержать строковую колонку `data`. Замените адрес и путь топика своими значениями, а компьютейшену привяжите ресурс `WriteYdb` с псевдонимом `YdbDriver`.

Для проверки записи передайте известное значение `data` через `events`, дождитесь фиксации эпохи Flow и прочитайте `processed-events` отдельным консьюмером YDB. Сообщение топика должно содержать переданное значение.

У синков по умолчанию `codec = "zstd"` и `compression_level = 4`. `ParseYdbCodec` и `DecompressYdbTopicMessage` из `cpp/helpers.h` преобразуют имя кодека и распаковывают сообщение. Формат framing выбирается отдельно от сжатия: у `TYdbFramingSink` и `TYdbAtLeastOnceFramingSink` по умолчанию `lenval`.

Framing-синки по умолчанию используют динамические пороги `max_rows_per_batch = 1000` и `max_bytes_per_batch = 5242880` (5 МиБ). Они задаются в параметрах синка по пути `DynamicSpec.computations/<computation>/sinks/<sink>/parameters`.

Параметры и значения по умолчанию:

- `TYdbSink`: [статические](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TUnitedParameters_NYT_NFlow_TYdbSink), [динамические](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TDynamicUnitedParameters_NYT_NFlow_TYdbSink).
- `TYdbFramingSink`: [статические](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TUnitedParameters_NYT_NFlow_TYdbFramingSink), [динамические](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TDynamicUnitedParameters_NYT_NFlow_TYdbFramingSink).
- `TYdbTwoPhaseCommitSink`: [статические](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TUnitedParameters_NYT_NFlow_TYdbTwoPhaseCommitSink), [динамические](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TDynamicUnitedParameters_NYT_NFlow_TYdbTwoPhaseCommitSink).
- `TYdbAtLeastOnceSink`: [статические](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TUnitedParameters_NYT_NFlow_TYdbAtLeastOnceSink), [динамические](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TDynamicUnitedParameters_NYT_NFlow_TYdbAtLeastOnceSink).
- `TYdbAtLeastOnceFramingSink`: [статические](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TUnitedParameters_NYT_NFlow_TYdbAtLeastOnceFramingSink), [динамические](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_TDynamicUnitedParameters_NYT_NFlow_TYdbAtLeastOnceFramingSink).

Публичный клиент, входящий в сборку, со стандартным набором кодеков поддерживает `raw`, `gzip` и `zstd`. Хотя парсер имён принимает `lzop`, кодировщик LZOP в клиенте по умолчанию не зарегистрирован. Для его использования приложение должно зарегистрировать совместимую реализацию через `NYdb::NTopic::TCodecMap::Set`, а сервер — поддерживать этот кодек.

### Гарантии доставки {#delivery}

Асинхронные `TYdbSink` и `TYdbFramingSink` сначала сохраняют выход в `output_messages` вместе с фиксацией эпохи Flow. Повторная отправка использует постоянные `producer_id` и `seqNo`, чтобы YDB дедуплицировала сообщения. Гарантия exactly once относительно эпох Flow предполагает сохранность состояния пайплайна и поддержку дедупликации на стороне топика.

Варианты at least once пишут напрямую. Если эпоха завершится ошибкой после записи, повторная обработка может записать те же сообщения ещё раз.

Асинхронные синки сохраняют `producer_id` в состоянии пайплайна и используют его как идентификатор производителя и группы сообщений YDB. После увеличения числа партиций старый идентификатор в некоторых случаях не позволяет писать в новые партиции. Для безопасной перегенерации обратитесь к команде Flow. Не очищайте состояние, не сбрасывайте `seqNo` и не заменяйте идентификатор вручную как универсальный способ восстановления.

`TYdbTwoPhaseCommitSink` использует протокол **отложенной публикации**, а не обычные транзакции топиков. Содержимое сообщений предварительно записывается на сервере и становится видимым после фиксации эпохи Flow. Сохранённое состояние позволяет продолжить публикацию после перезапуска. Синк не удаляет дубли, уже присутствующие во входном потоке.

Сервер должен поддерживать операции подготовки, публикации и отмены. В проверенной конфигурации релиза YDB `26.3.1.16-rc` для этого включён `config.feature_flags.enable_topic_deferred_publish`; без флага сервер отвечает `UNSUPPORTED`. Точная версия, контрольные суммы бинарного файла и конфигурации, а также результаты проверки возможностей зафиксированы в [server.lock.json]({{source-root}}/yt/yt/flow/extensions/ydb/test/server.lock.json). Поддержку другого развёртывания проверяйте отдельно до выбора этого синка.

[Генератор конфигурации публичного теста]({{source-root}}/yt/yt/flow/extensions/ydb/test/public_ydb.py) при включении отложенной публикации добавляет `feature_flags` в существующий корневой раздел `config`. Ниже показан соответствующий фрагмент MainConfig; объедините эти настройки с существующим разделом `config`:

```yaml
config:
  feature_flags:
    enable_topic_deferred_publish: true
```

Неопубликованные сообщения должны оставаться на сервере до завершения публикации: после истечения срока хранения восстановить их из состояния Flow нельзя. Ожидание недоступной цели может задержать завершение партиции. Не удаляйте состояние публикации, чтобы обойти ожидание: удаление не отменяет публикацию на сервере.

### Атрибуты и метаданные Flow {#attributes}

У вариантов без framing `attributes_column` указывает на YSON-колонку с пользовательскими атрибутами. `TYdbTopicAttributes` — словарь строковых имён и значений, `TYdbMessageMeta` — список пар строк. Функции из `cpp/attributes.h`:

- `PackYdbTopicAttributes` создаёт значение колонки и проверяет имена и лимиты;
- `UnpackYdbTopicAttributes` читает такое значение, в том числе из результата сорса;
- `ParseYdbTopicAttributesColumn` разбирает колонку синка; `null` означает отсутствие атрибутов.

Префиксы `_ytflow_` и `__` зарезервированы; исключение `__key` позволяет задать Kafka key. Framing-синки отвергают `attributes_column`; `TYdbTwoPhaseCommitSink` также отвергает его при заданном `framing_format`.

Параметр `write_flow_queue_meta` по умолчанию выключен. Он передаёт `EventTimestamp` и `EventWatermark` следующему пайплайну. Сорс принимает оба имени: `flow_queue_meta` и `_ytflow_queue_meta`; синк пишет `_ytflow_queue_meta`. Динамический `flow_queue_meta_heartbeat_period` по умолчанию равен `10s`.

## Ошибки настройки {#configuration-errors}

- `Static resource is not found` с `resource_id=YdbDriver`: проверьте `required_resource_ids` компьютейшена, псевдоним `YdbDriver` и флаг `controller` или `worker` для процесса, в котором возникла ошибка. Оба флага должны быть включены.
- `Configured token environment variable ... is empty` или `Configured password environment variable ... is empty`: задайте непустое значение указанной переменной; для Vanilla передайте её через `vanilla.secret_env`.
- `Column ... is already present in the topic source schema`: выберите имя `attributes_column`, отличное от имён выходных колонок сорса.
- `Framing does not support the "attributes_column" parameter`: в `TYdbTwoPhaseCommitSink` нельзя одновременно задать `framing_format` и `attributes_column`. Чтобы оставить framing, уберите `attributes_column`.
- `Failed to init session in time`: при инициализации очередной опрос не вернул событие, а время ожидания превысило `start_session_timeout` (по умолчанию `300s`).
- `Session is closed`: SDK закрыл сессию чтения; Flow передаёт ошибку со статусом и подробностями SDK в атрибуте `event`. Закрытие сессии отдельной партиции обозначается сообщением `Partition session is closed`.

При ошибках сессии чтения проверьте наличие топика и консьюмера, права на чтение и доступность адреса сервера. Если ошибка содержит статус и подробности SDK, изучите их. По одному внешнему сообщению об ошибке нельзя определить, какое из этих условий привело к сбою.

## Совместимость сохранённого состояния {#compatibility}

Идентификатор источника для `TYdbSource`, `TYdbMultiLineSource` и `TYdbFramingSource` вычисляется по `ydb-topic/v1`, `database` и `topic`. Консьюмер и класс сорса в него не входят. Ключ партиции содержит идентификатор источника, адрес сервера и индекс партиции. Сорс подключается к адресу, сохранённому в ключе. Смена одного из этих трёх классов другим сама по себе не начинает независимое чтение.

Для обычного топика новые ключи партиций содержат настроенный `endpoint`; его изменение меняет эти ключи. В именованной федерации используются адреса обнаруженных кластеров. При смене адреса обнаружения федерации ключи остаются прежними, только если адреса обнаруженных кластеров не меняются. Сама смена адреса обнаружения не подтверждает совместимость сохранённого прогресса.

Изменение `database` или `topic` меняет идентификатор источника и ключи партиций. Следуйте [правилам смены сорса](../../../flow/connectors/about.md#source-change): перед изменением статической спецификации остановите пайплайн; старые партиции завершатся, а новые начнут чтение независимо. Перед заменой сорса, не входящего в эти три публичных класса YDB, выполните полный drain и дождитесь состояния `Stopped`. Оффсеты прежнего сорса не переносятся, частичное использование его сохранённого состояния не поддерживается.

Перед сменой адреса сервера остановите джобы пайплайна. Если совместимость с сохранёнными ключами и состоянием не установлена, выполните полный drain до `Stopped` и обратитесь к команде Flow. Не переписывайте ключи и оффсеты вручную. Неизменённая спецификация сорса продолжает использовать своё состояние.

## Примеры и проверка {#examples}

Публичные [интеграционный тест]({{source-root}}/yt/yt/flow/extensions/ydb/test/integration/test_ydb.py), [шаблон пайплайна]({{source-root}}/yt/yt/flow/extensions/ydb/test/pipeline/pipeline.yson) и [компьютейшен на C++]({{source-root}}/yt/yt/flow/extensions/ydb/test/pipeline/main.cpp) показывают чтение protobuf-сообщений, их обработку и запись результата. Тестовая среда подставляет адреса, учётные данные и класс синка. Шаблон содержит подстановки и не предназначен для запуска без настройки.

Для пайплайна с `TYdbSource` и `TYdbSink`, который без изменений передаёт `data` из `events` в `processed-events`, используйте подготовленные выше топики и консьюмеров. После запуска этого пайплайна [запишите одно текстовое сообщение](https://ydb.tech/docs/ru/reference/ydb-cli/topic-write):

```bash
printf '%s' 'flow-check-message' | ydb --profile flow topic write events --format single-message
```

После фиксации эпохи Flow [прочитайте результат](https://ydb.tech/docs/ru/reference/ydb-cli/topic-read) отдельным консьюмером:

```bash
ydb --profile flow topic read processed-events --consumer flow-check --format single-message --limit 1 --wait --commit false
```

Для новых топиков ожидаемый результат — `flow-check-message`. Если результата нет, команда ждёт его появления. При необходимости прервите её сочетанием Ctrl+C и проверьте пайплайн и [ошибки настройки](#configuration-errors). Эти команды работают с обычными байтами сообщения и не проверяют protobuf или framing.
