# Библиотека framing в {{product-name}} Flow

Функции framing во Flow объединяют строки байтов в блоки и разбирают такие блоки обратно. Обычно строка байтов содержит сериализованное protobuf-сообщение. [Обёртки C++]({{source-root}}/yt/yt/flow/extensions/framing/cpp) используют [`library/cpp/framing`]({{source-root}}/library/cpp/framing). Используйте их, чтобы согласовать формат данных между компонентами и упаковать или распаковать сообщения в коде на C++.

Далее **фрейм** — это обрамлённая в выбранном формате строка байтов. В `lenval` перед данными стоит varint-длина, в `light_protoseq` — четырёхбайтовая длина little-endian, а в `protoseq` к четырёхбайтовой длине little-endian добавлен sync-маркер после данных. **Блок** — строка байтов из одного или нескольких фреймов; **батч** — группа сообщений, из которой функция формирует блок.

Общие функции задают формат блока и правила его обработки. Настройки конкретных коннекторов, их значения по умолчанию, сжатие и реакция на ошибку распаковки относятся к самим коннекторам и описаны на их страницах.

## Выбор формата {#format}

Общие функции C++ принимают элемент `NYT::NFlow::EFramingFormat`. Байтовые форматы описаны в [справочнике форматов](../../../flow/generated_docs/all_yson_structs.md#NYT_NFlow_EFramingFormat).

#|
|| **Формат** | **C++: `EFramingFormat`** | **Значение** ||
|| `auto` | `EFramingFormat::Auto` | `0` ||
|| `protoseq` | `EFramingFormat::Protoseq` | `1` ||
|| `lenval` | `EFramingFormat::Lenval` | `2` ||
|| `light_protoseq` | `EFramingFormat::LightProtoseq` | `3` ||
|#

Выбирайте формат по требованиям обеих сторон обмена:

- `lenval` подходит, когда нужен компактный блок; на принимающей стороне задайте `lenval` явно;
- `protoseq` позволяет возобновить чтение после частичного повреждения благодаря sync-маркерам; на принимающей стороне задайте `protoseq` явно. Форматы `lenval` и `light_protoseq` не позволяют восстановить границы фреймов после повреждения;
- `light_protoseq` нужно явно задать и при упаковке, и при распаковке: `auto` его не определяет;
- `auto` используйте только для распаковки данных неизвестного формата, если отправитель может прислать `protoseq` или `lenval`.

При упаковке `auto` не выбирает формат автоматически и не сохраняет исходный формат: это значение всегда означает `protoseq`. Поэтому `PackBatch` и `PackBatches` с `EFramingFormat::Auto` создают блок `protoseq`. Это поведение общих функций; оно не задаёт значение по умолчанию для коннектора.

{% note warning %}

Если формат известен, задавайте его явно. В режиме `auto` распаковщик сначала проверяет, начинается ли блок с корректного фрейма `protoseq`, и иначе выбирает `lenval`. Поэтому блок `lenval`, начало которого одновременно похоже на `protoseq`, может быть разобран неверно без ошибки.

{% endnote %}

## C++ API {#cpp-api}

Тип `EFramingFormat` объявлен в `yt/yt/flow/extensions/framing/cpp/public.h`, а функции — в `packer.h` и `unpacker.h` в том же каталоге. Все они находятся в пространстве имён `NYT::NFlow`.

### Упаковка одного блока {#cpp-pack-batch}

```cpp
std::string PackBatch(
    const std::vector<TOutputMessageConstPtr>& messages,
    const std::string& dataColumn,
    const EFramingFormat framingFormat);
```

`PackBatch` читает из каждого сообщения значение колонки `dataColumn`, без изменений передаёт его байты упаковщику, сохраняет порядок сообщений и возвращает один блок в формате `framingFormat`. Если в колонке хранится protobuf, сериализовать сообщение нужно до вызова функции. Колонка должна существовать. Значение, отличное от `null`, должно иметь тип `string`, иначе чтение завершится ошибкой; `null` читается как пустая строка и образует пустой фрейм.

### Разбиение на несколько блоков {#cpp-pack-batches}

```cpp
std::vector<std::pair<std::string, std::vector<TOutputMessageConstPtr>>> PackBatches(
    const std::deque<TOutputMessageConstPtr>& messages,
    const std::string& dataColumn,
    const EFramingFormat framingFormat,
    const i32 maxRowsPerMessage,
    const i32 maxBytesPerMessage);
```

`PackBatches` возвращает пары: упакованный блок и исходные сообщения, образовавшие его батч. Функция добавляет очередное сообщение в текущий батч, а затем завершает его, если выполнено хотя бы одно условие:

- число сообщений достигло `maxRowsPerMessage`;
- сумма `TOutputMessage::ByteSize` достигла `maxBytesPerMessage`.

Последний неполный батч тоже упаковывается. Для пустого входа пустой батч не создаётся.

`TOutputMessage::ByteSize` — оценка памяти всего сообщения Flow: метаданных и всех колонок payload, а не только `dataColumn`. `maxBytesPerMessage` задаёт порог для суммы этих оценок, а не строгий предел размера закодированного блока. Проверка выполняется после добавления сообщения, поэтому последнее сообщение может привести к превышению порога. Служебные байты выбранного framing-формата в эту сумму не входят.

### Распаковка {#cpp-unpack-batch}

```cpp
template <typename TProto>
TErrorOr<std::vector<TProto>> UnpackBatch(
    TStringBuf rawData Y_LIFETIME_BOUND,
    const EFramingFormat framingFormat);
```

`UnpackBatch<TProto>` разбирает фреймы из `rawData` в сообщения типа `TProto`. При успехе функция возвращает их в исходном порядке. Если protobuf-сообщение не разбирается или распаковщик пропустил байты между фреймами либо в конце блока, функция возвращает ошибочный `TErrorOr`. Ошибка пропущенных данных содержит атрибут `is_permanent=true`. Уже разобранные сообщения не возвращаются как частичный успешный результат.

Чтобы получить содержимое фреймов без разбора protobuf, вызовите `UnpackBatch<TStringBuf>`. В этом режиме функция проверяет только структуру framing и отсутствие пропущенных байтов. Произвольное содержимое синтаксически корректного фрейма возвращается без проверки protobuf.

Элементы результата `UnpackBatch<TStringBuf>` — представления байтов из `rawData`, а не копии. Исходный буфер должен оставаться в памяти и не изменяться, пока используются эти элементы. Аннотация `Y_LIFETIME_BOUND` позволяет компилятору диагностировать некоторые ошибки времени жизни, но не продлевает жизнь буфера. Результат `UnpackBatch<TProto>`, напротив, содержит самостоятельные объекты protobuf.

Framing не содержит контрольной суммы, поэтому ни один режим `UnpackBatch` её не проверяет. Если повреждённые данные образуют синтаксически корректный фрейм, режим `TStringBuf` возвращает их как есть; режим protobuf дополнительно принимает их только тогда, когда они разбираются как допустимое сообщение `TProto`.
