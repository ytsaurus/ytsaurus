# Безопасность и доступы Vanilla-операции {{product-name}} Flow

<span id="security"></span>


## Под каким пользователем работает Vanilla-операция {#identity}

Запускайте раннер Vanilla-операции от имени отдельной служебной учётной записи: операция, контроллеры и воркеры наследуют учётную запись запуска. Регулярно ротируйте её секреты, выдавайте только необходимые роли и используйте разные учётные записи для продакшена и препрода.

{% if audience == "internal" %}

Во внутренней инфраструктуре запускайте Vanilla-операцию от имени робота. Контроллеры и воркеры обращаются к {{product-name}} с токеном этого робота. Для доступа к другим сервисам, поддерживающим TVM, можно использовать TVM-приложение.

{% endif %}

## Секреты {#secrets}

Секреты аутентификации, включая `YT_TOKEN`, **никогда** не должны попадать в исходный код, конфиги в репозитории или образы.

Чтобы передать в джобы секреты (например, {% if audience == "internal" %}`TVM_SECRET` для доступа к Logbroker или{% endif %} собственный токен), перечислите имена соответствующих переменных окружения в `secret_env`:

```yson
"vanilla" = {
    "enable" = %true;
    "pool" = "<ваш-пул>";
    "worker" = {"count" = 5};
    "secret_env" = ["MY_TOKEN"];
};
```

Значения берутся из окружения запуска (того, кто выполняет команду), передаются в поле `secure_vault` спеки, с которой операция стартует, и внутри джобы доступны как обычные переменные окружения. В сохранённую спеку операции `secure_vault` не попадает: {{product-name}} вырезает его перед записью, поэтому постфактум значения секретов не видны ни в Cypress, ни через атрибуты операции. `YT_TOKEN` указывать не нужно — он доставляется автоматически.

`node_config` попадает в спеку Vanilla-операции как файл и загружается в файловый кеш, поэтому это не секретный канал: не передавайте через него `YT_TOKEN` или другие секреты.{% if audience == "internal" %} `TVM_SECRET` передавайте через `secret_env`; раннер прочитает значение из своего окружения и положит его в `secure_vault` операции.{% endif %}

## Аутентификация {#auth}

Vanilla-операция запускается под пользователем, выполнившим команду, — этот же пользователь должен иметь доступ к {{product-name}}. Отдельно настраивать аутентификацию контроллеров и воркеров, как в долгоживущем деплое, не требуется.

Для запуска обязателен [токен доступа](../../../../user-guide/storage/auth.md) к {{product-name}}: раннер берёт его из переменной `YT_TOKEN`, затем из `YT_SECURE_VAULT_YT_TOKEN` (её {{product-name}} задаёт через `secure_vault`, когда раннер работает внутри джобы), затем из файла, на который указывает `YT_TOKEN_PATH`, и в последнюю очередь из `~/.yt/token`. Если токена нет ни в одном из этих мест, запуск завершится ошибкой.{% if audience == "internal" %} TVM при запуске не используется: раннеру нужен именно OAuth-токен.{% endif %}

Для регулярного запуска выполняйте команду от имени отдельной служебной учётной записи, а не человека; требования к учётной записи перечислены в разделе [Под каким пользователем работает Vanilla-операция](#identity).

Общие шаги настройки аутентификации, в том числе для контроллеров и воркеров, развёрнутых вне Vanilla-операции, приведены в следующем разделе.

## Самоподписанный TLS-сертификат контроллера {#controller-self-signed-tls}

Если в `bus_server` не заданы ни `cert_chain`, ни `private_key` и шифрование не отключено, Flow автоматически создаёт самоподписанный сертификат контроллера. Сертификат и его отпечаток SHA-256 публикуются в полях `certificate_pem` и `certificate_sha256` записи лидера таблицы `<pipeline_path>/flow_control`. После перезапуска контроллера новая инкарнация получает новую пару сертификата и ключа. Приватный ключ остаётся в памяти процесса и не публикуется в таблице или конфигурации Orchid.

Значение `bus_server.encryption_mode = "optional"` по умолчанию допускает как TLS-соединения, так и соединения без шифрования. Если задать только `encryption_mode = "required"`, контроллер будет требовать TLS и продолжит использовать автоматически созданный сертификат. Эта настройка требует шифрования, но не настраивает доверие клиента к сертификату.

При прямом подключении клиент Flow проверяет контроллер по опубликованному сертификату. Чтобы требовать проверку сертификата при подключении через RPC- или HTTP-прокси, задайте `encryption_mode = "required"` хотя бы на контроллере или прокси, а на прокси задайте `verification_mode = "ca"` или `"full"`. Используйте [пользовательский сертификат](#controller-tls), подписанный доверенным для прокси центром сертификации.

## Пользовательский TLS-сертификат контроллера {#controller-tls}

Чтобы контроллер принимал RPC-соединения с вашим TLS-сертификатом, задайте в `bus_server` одновременно `cert_chain` и `private_key`. Полная пара заменяет [автоматически создаваемый самоподписанный сертификат](#controller-self-signed-tls). Неполная пара при включённом шифровании приводит к ошибке запуска.

Раннер обычно отправляет команды через RPC-прокси {{product-name}}, а UI и `yt flow` с HTTP backend — через HTTP-прокси. Оба прокси обращаются к контроллеру напрямую по RPC. Если прокси проверяет сертификат контроллера по CA, используйте сертификат, подписанный доверенным для прокси центром сертификации. TLS на участке клиент → прокси настраивается отдельно от участка прокси → контроллер.

Передайте PEM-цепочку сертификатов и соответствующий приватный ключ через переменные окружения. Добавьте следующий фрагмент к существующим настройкам `vanilla`:

```yson
"secret_env" = ["FLOW_TLS_CERTIFICATE", "FLOW_TLS_PRIVATE_KEY"];
"node_config" = {
    "bus_server" = {
        "encryption_mode" = "required";
        "cert_chain" = {"environment_variable" = "FLOW_TLS_CERTIFICATE"};
        "private_key" = {"environment_variable" = "FLOW_TLS_PRIVATE_KEY"};
    };
};
```

Если удалить из примера `cert_chain` и `private_key`, сохранив `encryption_mode = "required"`, контроллер будет требовать TLS с [самоподписанным сертификатом](#controller-self-signed-tls).

Значения переменных должны содержать сам PEM, а не пути к файлам. Доставка через `secret_env` описана в разделе [Секреты](#secrets).

Вместо `environment_variable` можно указать `file_name`, например `cert_chain = {file_name = "/run/secrets/controller-chain.pem"}` и `private_key = {file_name = "/run/secrets/controller-key.pem"}`. Файлы должны быть доступны внутри процесса, принимающего TLS-соединения. Если заданы оба поля, значение определённой переменной окружения имеет приоритет; при её отсутствии читается файл. Эта же конфигурация `bus_server` подходит для отдельно запущенного процесса контроллера.

Храните приватный ключ в секретном файле или переменной окружения. Не задавайте его через `private_key.value`: конфигурация узла доступна через Orchid, а `node_config` также сохраняется в файловом кеше. Ссылки `file_name` и `environment_variable` сохраняют в конфигурации только путь и имя переменной.

Для пользовательского сертификата контроллер не публикует `certificate_pem` в метаданных пайплайна. Если сертификат не опубликован, клиент Flow при прямом подключении не проверяет сертификат контроллера. При проверке `ca` или `full` прокси должен доверять CA, выдавшему сертификат; добавьте промежуточные сертификаты в PEM-цепочку. В режиме проверки `full` поле SAN сертификата должно содержать адрес, который проверяет клиент. Flow публикует RPC-адрес с IP. Чтобы использовать сертификат только на DNS-имя, задайте это имя в клиентской настройке `peer_alternative_host_name`.

## Минимально необходимые доступы {#permissions}

Учётной записи пайплайна нужны только те права, без которых пайплайн не сможет работать:

- роль на кластере {{product-name}} с правами на директорию пайплайна и пути всех таблиц, к которым он обращается;
- право запускать операции в нужном пуле{% if audience == "internal" %};{% else %}.{% endif %}

{% if audience == "internal" %}

- доступ на чтение и запись соответствующих топиков Logbroker, если используется коннектор Logbroker;
- доступ в проект Monitoring, в который пайплайн пишет метрики.

{% endif %}

Не выдавайте широкие права, например `root` на кластере: при компрометации они увеличивают поверхность атаки.

## Чтение логов и артефактов операции {#operation-acl}

Право `read` на операцию открывает stderr джобов и другие [артефакты операции](../../../../user-guide/storage/access-control.md#managing-operations), включая входные данные джобов и live preview. Для чтения логов песочницы через job shell также нужно `manage`. См. [Логи](../../../../flow/devops/vanilla/diagnostics/logs.md). Управление пайплайном и доступ к исходным таблицам требуют отдельных прав.

### Политика ACL операции {#operation-acl-policy}

При обычном запуске раннера с `vanilla.enable = %true` поле `vanilla.acl` необязательно:

- Если поле отсутствует или равно `#`, Flow не задаёт ACL операции и сохраняет стандартные права планировщика.
- `[]` передаёт явный пустой ACL.
- Непустой список задаёт всю явную политику со стандартной семантикой ACL операций. Поддерживаются права `read`, `manage` и `administer`.

Flow не переносит ACL пайплайна в операцию. Прямой API `StartFlowVanillaOperation` не задаёт `acl` и использует стандартные права планировщика.

Добавьте поле в имеющийся блок `vanilla`. Вместо `<runtime_group>` укажите существующую группу кластера исполнения. Включите в явный список всех нужных читателей.

```yson
acl = [{action = allow; subjects = ["<runtime_group>"]; permissions = [read];}];
```

### Проверки и границы кластеров {#operation-acl-validation}

Субъекты явного ACL должны существовать на кластере исполнения (`vanilla.runtime_cluster`, по умолчанию кластер пайплайна). Состав групп и теги субъектов на этом кластере должны соответствовать выбранной политике.

При обычном запуске раннер проверяет явно заданный ACL и его субъекты до загрузки файлов, завершения прежней операции и записи манифеста. Для пустого ACL проверка субъектов не требуется. При ошибке `Cannot use vanilla operation ACL on runtime cluster` исправьте указанные учётные записи или доступ к кластеру и повторите запуск. Отказ в правах самому пользователю запуска не считается ошибкой этой проверки.

### Проверка доступа читателя {#operation-acl-verification}

После запуска выполните команды с учётными данными читателя на кластере операции. Подставьте неизменяемый ID со страницы операции в UI и логин из вывода `whoami`.

```bash
yt --proxy <operation_cluster> whoami
yt --proxy <operation_cluster> check-operation-permission \
    --operation <operation_id> --user <login> --permission read --format json
```

Ожидаемое значение `action` — `allow`. При отказе проверьте применимые запреты, членство в группах и теги на кластере исполнения. Если право есть, но stderr недоступен, проверьте [наличие логов](../../../../flow/devops/vanilla/diagnostics/logs.md#finished-jobs).

### Срок действия ACL и восстановление {#operation-acl-lifetime}

В сохранённой спеке операции остаётся настроенный ACL, в том числе явный пустой список или отсутствие ACL. Изменения конфигурации и обновления бинарей не меняют права работающей операции. Обычный повторный запуск применяет текущую конфигурацию. `reanimate_vanilla_operation` использует сохранённый ACL без предварительных проверок обычного запуска. Восстановите отсутствующие субъекты на кластере исполнения и [проверьте доступ после восстановления](../../../../flow/devops/vanilla/releases.md#reanimate-acl). Для смены политики используйте обычный запуск.
