## Секреты {#secrets}

Секреты аутентификации, включая `YT_TOKEN`, **никогда** не должны попадать в исходный код, конфиги в репозитории или образы.

Чтобы передать в джобы секреты (например, {% if audience == "internal" %}`TVM_SECRET` для похода в Логброкер или{% endif %} собственный токен), перечислите имена соответствующих переменных окружения в `secret_env`:

```yson
"vanilla" = {
    "enable" = %true;
    "pool" = "<ваш-пул>";
    "worker" = {"count" = 5};
    "secret_env" = ["MY_TOKEN"];
};
```

Значения берутся из окружения запуска (того, кто выполняет команду), передаются в поле `secure_vault` спеки, с которой операция стартует, и внутри джобы доступны как обычные переменные окружения. В сохранённую спеку операции `secure_vault` не попадает: {{product-name}} вырезает его перед записью, поэтому постфактум значения секретов не видны ни в Cypress, ни через атрибуты операции. `YT_TOKEN` указывать не нужно — он доставляется автоматически.

`node_config` попадает в спеку Vanilla-операции как файл и загружается в файловый кеш, поэтому это не секретный канал: не передавайте через него `YT_TOKEN` или другие секреты.{% if audience == "internal" %} `TVM_SECRET` передавайте через `secret_env`; раннер прочитает значение из своего окружения и положит его в `secure_vault` операции.{% endif %}

## Аутентификация {#auth}

Vanilla-операция запускается под пользователем, выполнившим команду, — этот же пользователь должен иметь доступ к {{product-name}}. Отдельно настраивать аутентификацию контроллеров и воркеров, как в долгоживущем деплое, не требуется.

Для запуска обязателен [токен доступа](../../../../user-guide/storage/auth.md) к {{product-name}}: лаунчер берёт его из переменной `YT_TOKEN`, затем из `YT_SECURE_VAULT_YT_TOKEN` (её {{product-name}} задаёт через `secure_vault`, когда лаунчер работает внутри джобы), затем из файла, на который указывает `YT_TOKEN_PATH`, и в последнюю очередь из `~/.yt/token`. Если токена нет ни в одном из этих мест, запуск завершится ошибкой.{% if audience == "internal" %} TVM при запуске не используется: лаунчеру нужен именно OAuth-токен.{% endif %}

Для регулярного запуска выполняйте команду от имени отдельной служебной учётной записи, а не человека; требования к учётной записи перечислены в разделе [Под каким пользователем работает Vanilla-операция](#identity).

## Пользовательский TLS-сертификат контроллера {#controller-tls}

Чтобы контроллер принимал RPC-соединения с вашим TLS-сертификатом, задайте в `bus_server` одновременно `cert_chain` и `private_key`. Полная пара заменяет [автоматически создаваемый самоподписанный сертификат](#controller-self-signed-tls). Неполная пара при включённом шифровании приводит к ошибке запуска.

Раннер обычно отправляет команды через RPC-прокси {{product-name}}, а UI и `yt flow` с HTTP backend — через HTTP-прокси. Оба прокси обращаются к контроллеру напрямую по RPC. Прокси проверяет сертификат контроллера по CA. TLS на участке клиент → прокси настраивается отдельно от участка прокси → контроллер.

Передайте PEM-цепочку сертификатов и соответствующий приватный ключ через переменные окружения. Добавьте следующий фрагмент к существующим настройкам `vanilla`:

```yson
"secret_env" = ["FLOW_TLS_CERTIFICATE", "FLOW_TLS_PRIVATE_KEY"];
"node_config" = {
    "bus_server" = {
        "encryption_mode" = "required";
        "cert_chain" = {"environment_variable" = "FLOW_TLS_CERTIFICATE"};
        "private_key" = {"environment_variable" = "FLOW_TLS_PRIVATE_KEY"};
    };
};
```

Значения переменных должны содержать сам PEM, а не пути к файлам. Доставка через `secret_env` описана в разделе [Секреты](#secrets).

Вместо `environment_variable` можно указать `file_name`, например `cert_chain = {file_name = "/run/secrets/controller-chain.pem"}` и `private_key = {file_name = "/run/secrets/controller-key.pem"}`. Файлы должны быть доступны внутри процесса, принимающего TLS-соединения. Если заданы оба поля, значение определённой переменной окружения имеет приоритет; при её отсутствии читается файл. Эта же конфигурация `bus_server` подходит для отдельно запущенного процесса контроллера.

Храните приватный ключ в секретном файле или переменной окружения. Не задавайте его через `private_key.value`: конфигурация узла доступна через Orchid, а `node_config` также сохраняется в файловом кеше. Ссылки `file_name` и `environment_variable` сохраняют в конфигурации только путь и имя переменной.

Для пользовательского сертификата контроллер не публикует `certificate_pem` в метаданных пайплайна. При проверке `ca` или `full` прокси должен доверять CA, выдавшему сертификат; добавьте промежуточные сертификаты в PEM-цепочку. В режиме проверки `full` поле SAN сертификата должно содержать адрес, который проверяет клиент. Flow публикует RPC-адрес с IP. Чтобы использовать сертификат только на DNS-имя, задайте это имя в клиентской настройке `peer_alternative_host_name`.

## Минимально необходимые доступы {#permissions}

Учётной записи пайплайна нужны только те права, без которых пайплайн не сможет работать:

- роль на кластере {{product-name}} с правами на директорию пайплайна и пути всех таблиц, к которым он обращается;
- право запускать операции в нужном пуле{% if audience == "internal" %};{% else %}.{% endif %}

{% if audience == "internal" %}

- доступ на чтение и запись соответствующих топиков Logbroker, если используется коннектор Logbroker;
- доступ в проект Monitoring, в который пайплайн пишет метрики.

{% endif %}

Не выдавайте широкие права, например `root` на кластере: при компрометации они увеличивают поверхность атаки.
