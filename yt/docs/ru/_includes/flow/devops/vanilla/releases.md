# Обновления и релизы Vanilla-операции {{product-name}} Flow

## Обновление пайплайна {#update}

Чтобы выкатить новую версию, измените код или спеку и снова запустите ту же команду. Для vanilla-запуска используется стратегия make-before-break: новая операция готовится (бинарь загружается в кэш {{product-name}}), пока старая продолжает работать, после чего происходит переключение — старая операция завершается, и стартует уже подготовленная новая. За счёт этого даунтайм минимален, и отдельно останавливать пайплайн перед релизом не нужно.

При обычном запуске раннер проверяет явно заданный [ACL операции](../../../../flow/devops/vanilla/security.md#operation-acl) до загрузки файлов и завершения прежней операции. При ошибке предварительной проверки прежний деплой продолжает работать. Последующая ошибка отправки новой операции не запускает прежнюю автоматически.

Способом завершения **старой** операции управляет переменная окружения `YT_FLOW_GRACEFUL_UPDATE`: `1` (по умолчанию) — старый пайплайн дренируется (`stop`), `0` — ставится на паузу (`pause`); после этого старая операция отменяется.

## Восстановление операции {#reanimate}

Состояние пайплайна (например, `working`) хранится в [Cypress](../../../../user-guide/storage/cypress.md) отдельно от vanilla-операции и при её завершении не меняется. Поэтому если операцию отменили в обход лаунчера (вручную или внешней системой), пайплайн остаётся в рабочем состоянии, но прогресса не делает — исполнять его некому. Поднять такой пайплайн обратно **ровно той же версией** можно инструментом `reanimate_vanilla_operation`. При запуске лаунчер сохраняет в узле пайплайна манифест (спеку операции и ссылки на её файлы); инструмент читает этот манифест и переотправляет операцию, не требуя пересборки:

```bash
ya run yt/yt/flow/tools/reanimate_vanilla_operation -- \
    --cluster <cluster> --path //path/to/pipeline
```

Инструмент **отказывается работать, если по алиасу есть живая операция на выбранном целевом кластере исполнения**, а `YT_TOKEN` и значения переменных, перечисленных в `secret_env`, заново берёт из окружения запуска — в Cypress они не хранятся.

### Сохранённый ACL и учётные записи {#reanimate-acl}

Восстановление использует сохранённый ACL, в том числе явный пустой список или отсутствие ACL в спеке, без предварительных проверок обычного запуска. Восстановите отсутствующие субъекты на кластере исполнения, а после восстановления [проверьте эффективные права](../../../../flow/devops/vanilla/security.md#operation-acl-verification). Для смены политики используйте обычный запуск.

По умолчанию инструмент использует сохранённые кластер исполнения и роль прокси. Перед сменой кластера убедитесь, что прежняя операция завершилась. Проверка живой операции по алиасу действует только на целевом кластере.

1. Прочитайте исходный кластер исполнения из манифеста. Найдите неизменяемый `OperationId` прежней операции в сообщении `Started vanilla operation` в логах лаунчера или на странице операции в UI. В манифесте ID операции нет.
2. Запросите состояние по этому ID на исходном кластере.

   ```bash
   yt --proxy "<previous_runtime_cluster>" get-operation "<previous_operation_id>" --attribute state --include-runtime --format json
   ```

   Продолжайте только при `completed`, `failed` или `aborted`. Если кластер недоступен, восстановите доступ и проверьте состояние перед продолжением.
3. Отправьте операцию на целевой кластер исполнения. Подставьте кластер и путь пайплайна, целевой кластер операции и роль RPC-прокси.

   ```bash
   ya run yt/yt/flow/tools/reanimate_vanilla_operation -- \
       --cluster "<pipeline_cluster>" --path "<pipeline_path>" \
       --runtime-cluster "<operation_cluster>" --runtime-proxy-role "<runtime_role>"
   ```

Без `--runtime-proxy-role` сохраняется записанная роль. Если целевой кластер совпадает с кластером пайплайна, инструмент использует `--proxy-role` клиента пайплайна. Доступ определяют состав групп и теги субъектов кластера исполнения. До отправки операции инструмент перезаписывает манифест и заново размещает файлы при межкластерном запуске.

## Хотфикс {#hotfix}

Для быстрой выкатки хотфикса используйте `YT_FLOW_GRACEFUL_UPDATE=0`: тогда перед заменой старая операция ставится на паузу (`paused`), а не дренируется до `stopped`. Это допустимо при соблюдении условий:

* Изменение между старой и новой версией минимальное и легко проверяемое. В идеале &mdash; отличие в один коммит.
* Нет изменений в топологии пайплайна и в схемах стримов.
* Новая версия готова к обработке промежуточных сообщений, оставшихся от старой версии.
* Новая версия сохраняет детерминированность поведения в [Swift](../../../../flow/concepts/glossary.md#swift)-компьютейшенах — иначе без дрейна возможны потери или удвоения промежуточных сообщений.

## Восстановление после неудачной спеки {#recovery-from-bad-spec}

Если джобы пайплайна падают на каждой эпохе (например, из-за ошибки в статической спеке), пайплайн не может задренироваться и остаётся в состоянии `draining`, а обновление по умолчанию сначала останавливает пайплайн и только потом заливает новую спеку. Раскатить исправление штатным путём в такой ситуации нельзя — запуск падает по таймауту с ошибкой вида `Timed out after ... waiting for pipeline state "stopped"`.

Та же ошибка возникает, если пайплайн просто дренируется дольше таймаута (большой бэклог, источник ещё не опустел). Прежде чем отключать дрейн, убедитесь по логам джобов, что пайплайн действительно не может задренироваться: пауза оставляет промежуточные сообщения в очередях, а дрейн для того и нужен, чтобы этого избежать.

Исправление раскатывается в два шага:

1. Запустите обновление с `YT_FLOW_GRACEFUL_UPDATE=0`: пайплайн будет поставлен на паузу, а не остановлен, и новая спека применится без дрейна. Это обновление подчиняется ограничениям [хотфикса](#hotfix), в том числе запрету на изменение топологии и схем стримов, поэтому вносите только те изменения, которые вернут джобы в рабочее состояние.
2. Когда джобы снова работают и пайплайн способен задренироваться, изменения топологии и схем стримов раскатывайте обычным обновлением с дрейном.
