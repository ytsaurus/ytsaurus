If the jobs are healthy but processing runs at a suspiciously low rate, or if the `Stream Time Lag` or `Event Watermark Lag` charts on the `Monitoring` tab of the `General` dashboard show increasing lag, processing is falling behind.

On the `Graph` tab of the pipeline UI, locate the slow `computation` and check the warnings and errors in the `Messages` sections. View the metrics for the causes below on the `Monitoring` tab, primarily in the `Epoch parts time` chart.

All messages passed between pipeline `computation`s are stored in memory, so their number is limited. As a result, a `computation` later in the pipeline can slow down an earlier one. Investigate the later `computation`s first.

Processing can fall behind for the following reasons:
* Insufficient processing resources. The bottleneck can be:
  * Overall CPU and network usage. Check whether any of these resources are being wasted and can be saved. You can also add more resources.
  * CPU or network usage on a small number of hosts. This issue is visible in the `Total VCPU (Worker)` and `Network bandwidth (Worker)` charts, although the deployment system charts are preferable. This is most likely a balancing problem. You may only need to wait for the built-in CPU balancing to finish.
  * A single CPU core. This issue is visible in the `Max partition cpu usage` chart. If a single partition has an excessive load, it slows down all processing. Consider increasing the number of partitions, especially if many partitions are under high load. The load can also be concentrated on one [key](../../../flow/concepts/glossary.md#key), known as a [heavy hitter](../../../flow/concepts/spec.md#heavyhitters). This can only be fixed in user code. Increasing the number of partitions does not split such a key across partitions.
  * Input or output buffers that are too small. This issue is visible as a large share of `Distribute.OutputBufferOverflow` or `Distribute.OutputStoreOverflow` in `Epoch parts time` for the `computation` sending messages. Buffer overflow can be caused by the next `computation` running slowly, so check it first. Choose buffer sizes based on the actual processing latency and required throughput. The buffer settings are described [here](../../../flow/concepts/spec.md#bufferstatemanager).
* Slow operations in {{product-name}}.
* Slow event reads from an external source. In the `Epoch parts time` chart for `source` computations, check whether they spend time waiting in `Input.Fetch`. If they do, contact the Flow team.
* The read window for an external source has been reached. If `Epoch parts time` shows a significant wait in `Input.ReadWindow`, the span in `alignment timestamp` values from the first message that has not yet been persisted to the last message read has reached `dynamic_spec.computations.<computation_id>.parameters.max_read_window`. This happens because commits are intentionally infrequent later in the pipeline, or because one or more downstream partitions are slow. Increase [this dynamic parameter](../../../flow/concepts/spec.md#parameters) only in the first case, when a wide span is expected. In the second case, find and fix the slow partitions.
* Insufficient distributed throttler quota. If `Epoch parts time` shows a significant wait in `Input.Throttle`, check the [Distributed Throttler](../../../flow/concepts/distributed_throttler.md) limits and metrics.
* Slow writes to an external queue. In the `Epoch parts time` chart for computations with `sink`s, check whether they spend time waiting in `Distribute.OutputBufferOverflow` or `Distribute.OutputStoreOverflow`. The pipeline may be exceeding the queue's write quota, or the queue may have too few partitions for the required write rate.
* Configured delay logic. `Input.InjectionDelay` and `Input.WatermarkAlignment` in `Epoch parts time` mean that processing is waiting because of the `watermark_strategy.watermark_alignment.read_delays` or `drift_bound` settings. Check these settings in the static pipeline spec ([WatermarkAlignment](../../../flow/concepts/spec.md#watermark-alignment)).
* Processing a single message batch takes a long time because it depends on an external system. For example, if each batch requires a request that takes 10 seconds and the batch size is limited to 1,000 messages, the maximum partition processing rate is 100 messages per second. In this case, increase the batch size, increase the number of partitions, reduce processing latency, or combine these approaches. The charts show the following symptoms: the partition spends a large share of its time (60% or more) in user code (`Process` in `Epoch parts time`), while its CPU usage is low (less than 0.3).
