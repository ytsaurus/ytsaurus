# Локальная проверка документации YT

Ты отвечаешь только за локальную проверку изменённой документации YT и YTsaurus. Не исследуй продукт, не редактируй содержание статьи, не создавай коммиты и PR.

Перед началом прочитай `yt/docs/AGENTS.md` целиком. Команды и правила выбора сборки из него — источник истины. Если они изменились, следуй актуальной версии `AGENTS.md`, а не примерам из этого скилла.

## Определи область проверки

Получи от вызывающего процесса список файлов, изменённых в текущей задаче. Если список не передан, посмотри текущее состояние Arc, но не считай все найденные изменения своими. Если нельзя однозначно отделить текущую задачу от посторонних правок, запроси список файлов.

Выбери сборочную цель по правилам `yt/docs/AGENTS.md`:

- для строго внутренней статьи без изменений общих файлов — Internal-сборку;
- для Public, общих исходников, инклудов, оглавления, пресетов или ресурсов — корневую сборку Public и Internal;
- для смешанных изменений — корневую сборку;
- если менялись только AI-артефакты, которые не входят в YFM-сборку, отметь проверку как неприменимую и не запускай `ya make` без причины.

Не запускай `build-and-serve*.py` и другие долгоживущие серверы предпросмотра: они предназначены для ручного просмотра, а не для автоматической проверки.

## Запусти сборку

1. Запусти выбранную команду из указанной в `AGENTS.md` директории.
2. Если сборка завершилась успешно, зафиксируй команду и проверенную область.
3. Если сборка упала, найди первую содержательную ошибку и определи, относится ли она к файлам текущей задачи.
4. Механическую ошибку в изменённых файлах — например, битую относительную ссылку, якорь, элемент оглавления или YFM-разметку — можно исправить, если решение однозначно и не меняет смысл текста. Непосредственно перед исправлением перечитай актуальный файл и сохрани все внешние изменения.
5. Если исправление требует продуктового решения, изменения содержания или затрагивает посторонний файл, ничего не угадывай: верни ошибку вызывающему процессу как блокер.
6. После любого исправления повтори применимую сборку. Успех предыдущего запуска не относится к файлам, которые менялись после него.
7. После последней успешной сборки вычисли SHA-256 каждого проверенного файла текущей задачи. Если файл изменится позже, результат этой проверки станет недействительным.

Не создавай PR с известной ошибкой сборки.

## Сообщи результат

Верни вызывающему процессу ровно один JSON-объект без Markdown-ограды и пояснений до или после него:

```json
{
  "build_checked": true,
  "status": "passed",
  "scope": "public_and_internal",
  "working_directory": "yt/docs",
  "command": "../../ya make",
  "attempts": 1,
  "validated_files": [{"path": "", "sha256": ""}],
  "files_fixed": [],
  "error": null,
  "notes": ""
}
```

Заполняй поля так:

- `build_checked` — `true`, если команда сборки запускалась, иначе `false`;
- `status` — `passed`, `failed` или `skipped`;
- `scope` — `public_and_internal`, `internal` или `not_applicable`;
- `working_directory` и `command` — фактически использованные значения, для `skipped` — `null`;
- `attempts` — количество запусков сборки, для `skipped` — `0`;
- `validated_files` — пути и SHA-256 файлов в состоянии после последней успешной сборки, для `failed` и `skipped` — пустой список;
- `files_fixed` — пути файлов, исправленных во время проверки;
- `error` — ключевая строка последней ошибки или `null`;
- `notes` — причина пропуска, блокер или другое краткое пояснение.

Это результат локальной сборки, а не финальный JSON-отчёт `write-draft-doc`. Вызывающий процесс использует его в общем отчёте по задаче.
