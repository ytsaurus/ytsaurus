# Отбор содержания и проверка полезности

Читай при выборе состава существенных изменений и перед независимой проверкой текста.
Проверка нужна, чтобы убрать лишнюю работу читателя и сохранить необходимые действия.
Короткий текст с пропущенным шагом хуже полного; длинный текст не обязательно полнее.

## От темы к изменению документации

Определи, какую задачу помогает решить материал. Учитывай знания, условия и права,
необходимые для понимания и выполнения описанных действий. Уточняй аудиторию, когда
это влияет на содержание; точное определение роли читателя не обязательно.
Проверь применимость к продукту, подтверждённое поведение и существующее место
в документации. Выбирай минимально достаточное изменение.
Решение «не включать» обосновывай так же, как добавление новой страницы. Явный запрос
пользователя нельзя молча отменить со ссылкой на минимализм.

Ниже — примеры применения правил отбора содержания, а не перечень допустимых
аудиторий и задач. Опирайся на текущий запрос, контекст продукта и исследование;
не подгоняй читателей и их задачи под примеры из таблицы.

| Ситуация | Пример обоснованного решения | Ошибка |
| --- | --- | --- |
| Черновик перечисляет новые функции встроенной библиотеки | Проверить доступность через продукт и пользу для его читателя; при необходимости дать пример или ссылку | Перенести весь список или запретить любые примеры зависимостей |
| В реализации найдено различие между конфигурацией сервиса и кодовым значением | Подтвердить область действия; описать нужное читателю поведение, доказательства оставить в исследовании | Объявить константу универсальным default или перенести в статью всё расследование |
| Пользователь просит обновить приложение | Описать подтверждённые действия и наблюдаемый результат; общую инструкцию сохранить пригодной для следующих версий | Добавить обязательный регламент, условный срок или диагностический запрос без источника |
| Администратор восстанавливает сервис | Сохранить необходимые команды, последовательность, права, проверки и ограничения | Удалить объяснение механизма, без которого нельзя безопасно выполнить восстановление |
| Процедура заканчивается словами «завершите операцию» | Добавить подтверждённое действие либо точную ссылку; при отсутствии источника зафиксировать пробел вне статьи | Назвать инструкцию полной или придумать команду |
| Постановщик не знаком с продуктом | Принести рекомендацию с основанием; неизвестное поведение адресовать эксперту | Просить выбрать между непонятными терминами и считать выбор доказательством |

## Задание независимому проверяющему

Ты не писал статью и не проводил её исходное исследование. Получи запрос, цель,
известные сведения о читателях, необходимые знания, условия и права, границы работы
и пути актуальных файлов. Не требуй названия роли читателя; проверяй, достаточно ли
описанных условий для понимания и выполнения действий. Читай полный
затронутый раздел вместе с контекстом, а не только добавленные строки. Для Public
проверь обе версии. Не читай самооценку автора и не принимай фактчек за оценку полезности.

Проверь:

1. Введение помогает решить, подходит ли возможность для задачи читателя.
2. Для каждого обязательного действия указаны необходимые условия и права,
   понятен способ выполнения. Есть необходимые начало, завершение и наблюдаемый результат.
3. Детали реализации помогают действию, диагностике или пониманию модели. Их нельзя
   удалять только за техническую сложность, особенно из администраторской инструкции.
4. Возможности зависимостей описаны в контексте продукта; не возникает ложного обещания
   поддержки. Не утверждай отсутствие поддержки без фактической проверки — задай вопрос.
5. Нет повторения соседнего справочника, необоснованного расширения процедуры и
   деталей, которые не меняют действий или понимания читателя.
6. Версия обозначает реальное ограничение или пример. Обычное обновление номера релиза
   не должно требовать переписывания общей процедуры.
7. Незакрытое неизвестное не замаскировано уверенной формулировкой, служебной оговоркой
   или требованием к читателю самому выяснить неописанный контракт продукта.

Для замечания укажи место, конкретную проблему для читателя, основание и действие:
исправить, добавить необходимый шаг, удалить, сократить, перенести, сослаться или уточнить.
Не требуй разделов и примеров лишь потому, что они присутствуют в шаблоне.
Не вводи новые продуктовые правила, сроки и команды: технические предложения требуют
проверки источниками. Если удаление меняет согласованный объём, отметь это явно.

Формат `content_review` — в [reports.md](reports.md). `passed` возможен только при
отсутствии содержательных проблем в проверенной области. Необязательное предпочтение
по формулировке можно оставить в `notes`, не объявляя его блокирующим дефектом.
