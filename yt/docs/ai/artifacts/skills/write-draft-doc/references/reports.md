# Отчёты и готовность

Отчёты служат доказательствами выполненных проверок. Храни их локально вне публикационного
дерева и не включай результаты прогонов в коммит документации. Пользователю показывай
краткий результат; подробности доступны по запросу. Секреты и токены в отчёты не записывай.

## Исследование

`research`: `status` (`complete`, `needs_input`, `failed`), `sources` (путь, символ,
версия/ревизия и подтверждаемый вывод), `user_cases`, `constraints`, `open_questions`.
Для инструкции необходим подтверждённый путь от исходных условий до результата.
Для небольшого справочного дополнения не придумывай сквозной сценарий ради поля отчёта.

Решения об отборе можно хранить здесь же: тема, задача читателя, источник, целевое место,
решение и причина. Вопрос содержит доказательства и указывает зависимый фрагмент.

## Проверки

Общие поля `content_review`, `fact_check`, `example_test`:

```json
{
  "status": "not_run",
  "scope": [],
  "validated_files": [],
  "issues": [],
  "open_questions": [],
  "evidence": [],
  "notes": ""
}
```

- `scope` — проверенные разделы, утверждения или сценарии; не выдавай выборочную
  проверку за проверку всего документа.
- `validated_files` — записи с `path` и `sha256`. При повторной проверке фиксируй
  текущие хеши; перенос результата требует доказать неизменность именно его области.
- `issues` — место, проблема, последствия для читателя, основание и предложенное действие.
- `example_test` дополнительно содержит `example_runs`: для каждого примера `location`,
  `status`, `environment`, `product_version`, `commands`, `expected`, `actual`.

Статусы: `passed` — проверка выполнена, содержательных замечаний и вопросов нет;
`failed` — обнаружен дефект; `needs_input` — не хватает конкретного условия или ответа;
`not_run` — проверка применима, но пока не выполнялась; `not_applicable` — неприменима
с указанной причиной. Не используй `not_applicable` вместо отсутствующей среды.
Если одновременно есть дефект и блокер, ставь `failed`, а блокер сохраняй в вопросах.

Для исполнения `passed` требует реального успешного запуска каждого применимого
примера. Отсутствие запуска нельзя компенсировать чтением кода, пустым списком примеров
или успешной сборкой. Для справочника без изменённых исполнимых примеров запуск неприменим.

## Краткий итог при изменении файлов

Сохрани прежние поля итогового отчёта и явно раздели виды проверок:

```json
{
  "files_changed": [],
  "task_tier": "targeted",
  "diataxis_type": "reference",
  "draft_prepared": false,
  "goal_achieved": false,
  "what_why_covered": false,
  "content_review": "not_run",
  "fact_check": "not_run",
  "example_test": "not_applicable",
  "content_validation": "not_run",
  "build_status": "not_run",
  "nda_check": "not_run",
  "styleguide": "skipped",
  "deviations": [],
  "open_questions": [],
  "pr_url": "",
  "notes": ""
}
```

`draft_prepared` означает наличие обсуждаемого текста; `goal_achieved` — весь
согласованный результат получен и все обязательные проверки прошли на актуальных файлах.
`what_why_covered` подтверждается проверкой полезности. Для тривиальных правок содержательные
проверки могут быть неприменимы; объясни это в `notes`. `styleguide=skipped` означает
отказ от дополнительной редактуры, а не отказ от базовой понятности текста.

`content_validation` агрегирует три содержательные проверки: при любом `failed` —
`failed`, иначе при любом `needs_input` — `needs_input`, затем при любом `not_run` —
`not_run`; если все неприменимы — `not_applicable`, иначе — `passed`.
У `goal_achieved=true` не может быть незакрытой части запроса или применимой проверки
со статусом `failed`, `needs_input`, `not_run`, включая требуемую сборку и RU/EN-паритет.
Допустимость раннего неопубликованного PR этого условия не меняет.

Отчёт `validate-doc-build` имеет свой формат: его `status=skipped` вместе с
`scope=not_applicable` отображай в итоговый `build_status=not_applicable`, сохранив
причину. Иные пропуски сборки не считаются неприменимостью: укажи `not_run` либо
`needs_input` по фактической причине. `passed`/`failed` переноси без изменения.
